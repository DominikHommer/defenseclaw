DefenseClaw has one persisted connector fail-mode policy, installed with the
hooks, plus one environment variable that can only make an outage stricter
(see [The environment does not set the fail mode](#the-environment-does-not-set-the-fail-mode)).
The effective connector mode applies consistently to both transport and
invalid-response failures.

## Controls

| Control | Effect | Default and scope |
| --- | --- | --- |
| `guardrail.hook_fail_mode` | `open` allows or `closed` blocks supported hook events when delivery or the gateway response fails. | `closed` on a fresh install. Migrated legacy configs can retain explicit `open`. Secure Client deployments default to `open` when it is unset (see [Secure Client](#secure-client)). Can be overridden per connector. See [Which value applies](#which-value-applies). |
| `DEFENSECLAW_STRICT_AVAILABILITY=1` | Forces transport and missing-token failures closed on a hook that can block. It cannot force an otherwise closed connector open. Not every hook reads it: see the [gateway outage table](/docs/connectors/capability-matrix#gateway-outage). | Unset. Per agent process; compatibility/managed-deployment override. |
| `DEFENSECLAW_FAIL_MODE` | Not read by 1.0.4 hooks: the installed mode is the fail mode. Hooks rendered by 1.0.3 or earlier read it until the upgrade renders them again; Secure Client shell hooks keep it (see [The environment does not set the fail mode](#the-environment-does-not-set-the-fail-mode)). | Set the mode with `defenseclaw guardrail fail-mode`. |

You choose `open` or `closed`, and the default is `closed`. An explicit value
always wins, on every install: the OSS per-user install, the standalone
enterprise profile, MDM-managed standalone hosts and Secure Client. On a
managed computer the value comes from the administrator's config (the managed
`config.yaml`, which only root or SYSTEM can change, delivered by the
installer, `ensure`, a signed policy bundle or an MDM/Intune payload), so an
`open` there is the administrator's choice. What each connector's hooks do
with it during an outage, per install, is in the [gateway outage table](/docs/connectors/capability-matrix#gateway-outage):
some managed Linux and macOS hooks block an outage whatever the administrator
chose.
A fail mode that is not set is `closed` everywhere except under Secure
Client, where it is `open` (see [Secure Client](#secure-client)).

`status --json` and `verify --json` give the resolved fail mode of each
connector a managed deployment protects as
`connectors.<id>.effective_hook_fail_mode`. That is the administrator's
resolved value, so it can say `open` for a hook that blocks an outage in every
fail mode.

Some refusals do not depend on the fail mode, because they are not an outage:
on a managed computer a hook still blocks when its administrator-owned runtime
(the runtime descriptor on Linux and macOS, the runtime generation on
Windows) is missing or fails its checks, when another program answers in
place of the gateway service, when its token is missing, when the gateway
refuses its credential (HTTP 401 or 403, also when the rest of that answer is
cut off or too large), when the call does not match the
event or hook contract the hook was registered for, and when the account is
not enrolled. An unapproved hook that the foreign-hook
guard finds blocks in every fail mode too, and so does a call the guard cannot
check against the agent session's hook record because the gateway cannot
answer (on a standalone host with `foreign_hooks: remove`, for the connectors
the [foreign-hook guard](/docs/enterprise/foreign-hook-guard#which-connectors-it-covers)
covers): only the gateway holds that record, and a session it blocked may still run the hook it loaded.

On a managed standalone host `open` applies only to an outage: the gateway
service is not running, is still restarting, or gives no answer in time
(the [gateway outage table](/docs/connectors/capability-matrix#gateway-outage) says which hooks let such a call run).
Every other failure blocks in fail mode `open` too, for every connector:
tool input over the hook's 1 MiB limit, a gateway error status (5xx), an
answer DefenseClaw cannot use, and any other transport error. Per-user and
Secure Client hooks are unchanged.

On a managed standalone host the fail mode is the administrator's installed
`hook_fail_mode`, and `DEFENSECLAW_FAIL_MODE` in the agent's environment does
not change it: `closed` there does not close a hook the administrator set to
`open`. To block during an outage, set
`hook_fail_mode: closed` (the default) in the admin config, or use the
separate [strict availability](#strict-availability) setting,
`DEFENSECLAW_STRICT_AVAILABILITY=1`, which the hooks that read it honor
because it can only close (see the [gateway outage table](/docs/connectors/capability-matrix#gateway-outage)). See
[Environment variables](/docs/reference/env-vars).

<Callout type="warning" title="Older transport-only descriptions are stale">
The effective hook fail mode now covers connection refusal, timeout, gateway
5xx, missing authentication, unauthorized/malformed responses, and a missing
decision field. `closed` no longer silently opens only because a failure was
classified as transport.
</Callout>

### Which value applies

Each connector's effective fail mode resolves in this order, in observe and
action mode alike:

1. On a managed computer, the automatic-protection value
   (`application_protection.connectors.<name>.guardrail.hook_fail_mode`, or
   `application_protection.guardrail.hook_fail_mode`) for a connector it
   protects.
2. The connector's own value (`guardrail.connectors.<name>.hook_fail_mode`),
   set with `guardrail fail-mode open|closed --connector <name>`.
3. Otherwise, the global `guardrail.hook_fail_mode`.
4. Otherwise `closed` outside Secure Client. A fail mode that is not set never
   opens a hook there, also for a connector in observe mode. Under Secure
   Client an unset value is `open`.

Any value other than `open` (in any case) is `closed`. The
[gateway outage table](/docs/connectors/capability-matrix#gateway-outage) lists the per-user hooks that follow their
guardrail mode instead.

<Callout type="info" title="Changed in 1.0.3">
On a managed computer outside Secure Client an explicit
`hook_fail_mode: open` is honored. Earlier 1.0.3 builds ignored it there and
reported it as `fail_open_ignored`; that warning is gone. An upgrade does not
write `open` into a managed config: the config_version 9 migration keeps a
managed Cursor fail mode as the administrator wrote it. The 1.0.0 to 1.0.2
migration rewrote it from the guardrail mode (observe became `open`); the
first 1.0.3 `ensure` sets such a value back to `closed` when
`migration-v9.json` records that rewrite and `config.yaml` is still the
migration's output, says so in its changes, and never touches an `open` the
administrator wrote later.
</Callout>

<Callout type="info" title="Changed in 1.0.3">
Before 1.0.3 a per-user connector in observe mode without its own fail mode
stayed `open`, whatever the global value said. From 1.0.3 it follows the
global value and is `closed` when none is set. To keep an observe-mode
connector fail-open, set it explicitly:
`defenseclaw guardrail fail-mode open --connector <name>`.
</Callout>

### Secure Client

Under the Secure Client integration only, hooks fail open: an unset
`guardrail.hook_fail_mode` resolves to `open` for every connector (Codex and
Claude Code included), independent of the guardrail mode, and an explicit
`closed` (global or per connector) is always kept. With `open`, a Secure Client
hook allows the call when the gateway is unreachable, its service is stopped
or its answer cannot be used, and records the failure.
Only an authenticated Secure Client deployment gets this: the profile the
protected config resolves and, for the native Windows hook, a host whose
Secure Client installation, deployment record and gateway service check out.
The administrator owns that config, and the gateway resolves its default.
Every other install, including OSS, the standalone enterprise profile and
MDM-managed standalone hosts, keeps the closed default above.

An agent that gives a hook no way to fail closed lets the call run in
`closed` too: `guardrail fail-mode closed` saves `closed` for it only as the
requested value, and `guardrail fail-mode` shows it as upstream fail-open. The
[gateway outage table](/docs/connectors/capability-matrix#gateway-outage) says which connectors that is, per install. An
agent can also run a call when its hook times out or cannot start; see the
[residual risks](/docs/enterprise/threat-model#residual-risks).

A managed standalone host is stricter: in `closed` (also when no value is
set) its hooks block a tool call DefenseClaw cannot check (the gateway service
is not running, its answer cannot be used, or the call is too large to
inspect), on Linux, macOS and Windows alike, and the agent shows why, for
example that the DefenseClaw gateway service is not running on this computer.

A managed GitHub Copilot hook whose registered command names no Copilot event
DefenseClaw reviewed (a registration DefenseClaw did not write) is refused in
every fail mode. Copilot can block only `preToolUse` and `permissionRequest`,
and its payload does not say which event it is, so the hook answers with both
of Copilot's deny fields; Copilot's other events cannot block. `verify`
reports a DefenseClaw hook in the policy drop-in that is registered for an
event DefenseClaw does not publish, and `ensure` rewrites the drop-in.

## Effective behavior

| Failure | Effective `open` | Effective `closed` |
| --- | --- | --- |
| Gateway connection refused, timeout, or 5xx | Allow the event, warn, and record the transport failure. When the gateway starts again it reports the allowed calls as an alert (see [Reporting and diagnosis](#reporting-and-diagnosis)). | Return the connector's block response and record the transport failure. |
| Connector authentication is missing | Allow by default and record the missing-token failure. | Block and report token/authentication failure. |
| Gateway returns 4xx, malformed JSON, or no action | Allow, warn, and record the response failure. | Block with the connector's response shape and record the failure. |
| Hook input exceeds its bounded payload | Refuse to process it, record the condition, and allow. | Refuse to process it, record the condition, and block where the connector supports a block response. |
| Valid gateway verdict | Honor the connector/event mapping. | Honor the same mapping. Fail mode does not turn an observation-only event into a blocking surface. |
| Internal policy evaluator error (a recovered panic) | Allow with `would_block`, a warning, an audit row with result `panic`, and telemetry. | Block when the event supports a block response; otherwise allow with `would_block`. Record an audit row with result `panic` and telemetry either way. Secure Client allows and audits recovered errors. |
| Ordered-chain state unavailable or inconsistent | Preserve the current event's standalone verdict; skip only the chain join. | The same standalone verdict. Chain storage never fabricates or removes a single-event block. |

### Stop and session-end events

A block on a stop or session-end event denies nothing. Codex, Claude Code,
Devin and GitHub Copilot continue the turn when a stop hook blocks, and Cursor
submits the block as the next prompt, so an agent whose stop hook failed
closed tried to stop again on every model turn, each costing a model call,
until the user interrupted it.

When a hook would fail closed on one of these events because the gateway is
down or answers 5xx, its answer is unusable or the hook token is missing, it
gives the agent's neutral allow instead and says on stderr that it is not
blocking the event. Per-user hooks on Linux, macOS and Windows also record the
failure in `hook-failures.jsonl` with fail mode `open`. In 1.0.3, OpenShell
sandbox hooks and standalone managed hooks do not persist that failure row;
that logging gap is a P3 follow-up for 1.0.4. The agent ends the turn, and the
next prompt or tool call is blocked as before until DefenseClaw is available.
The neutral allow holds for per-user, OpenShell sandbox and standalone managed
hooks on Linux, macOS and Windows. Secure Client hooks follow their fail mode.

The hook has to know the event first. Codex and GitHub Copilot name it in the
registered hook command; the other connectors read it from the payload's
`hook_event_name` or `event` field. So these cases still block:

- A payload that is too large to read, or a DefenseClaw home that is
  unavailable, for connectors that read the event from the payload.
- A missing hook token for the Devin and Kiro hooks on Linux and macOS, which
  check the token before they read the payload, and in the OpenShell sandbox.
- A payload whose event fields are not strings or name different events, and
  a Codex payload that does not match the event of its registered command.

| Connector | Stop and session-end events |
| --- | --- |
| Claude Code | `Stop`, `SubagentStop`, `TeammateIdle`, `StopFailure`, `SessionEnd` |
| Codex | `Stop`, `SubagentStop`, `SessionEnd` |
| Cursor | `stop`, `subagentStop`, `sessionEnd` |
| Devin | `Stop`, `SessionEnd` |
| GitHub Copilot | `agentStop`, `subagentStop`, `sessionEnd` |
| Kiro | `Stop` |
| OpenCode (managed plugin) | `session.created`, `session.updated`, `session.status`, `session.idle`, `session.compacted`, `session.error`, `session.deleted` |

A gateway verdict on these events is unchanged: fail mode does not apply to a
valid answer.

Fail mode applies only to a hook the agent can start. A hook script that is
missing, cannot be read or is not executable (an antivirus quarantine, a
restored backup with the wrong mode, an account rename or home move that left
the agent hooks pointing at the old home) makes the shell exit 126 or 127,
which Claude Code and the other agents treat as a non-blocking hook error: the
tool call runs unguarded whatever the fail mode. `defenseclaw guardrail
status`, `defenseclaw status` and `defenseclaw doctor` say that the connector
is not guarded and name the repair (`defenseclaw doctor --fix` restores the
script mode; `defenseclaw setup <connector>` or `defenseclaw-gateway restart`
renders the scripts and re-points the hooks after a home move).

On a managed Linux or macOS host the hook is the administrator-owned
`defenseclaw-hook` binary. When it is missing, empty (agents run an empty
file as a script that allows every call), not executable, not owned by root
or not the binary the deployment installed (hash mismatch),
`enterprise linux status` (or `macos`) and `verify` fail with the path, the
state and `security_complete: false`, and the hook guardian starts the
lifecycle's config-apply job within seconds, which puts the binary back from
the copy the lifecycle sealed when it committed the deployment (checked
against its recorded SHA-256 before it is made executable, then renamed into
place as root with mode 0755). `enterprise linux repair` does the same at
once. On Windows the standalone guardian puts a missing, empty or different
`defenseclaw-hook.exe` back from its protected copy within seconds.

A recovered hook evaluation error now honours the fail mode. In action mode,
`closed` blocks an event that supports a block response; `open` allows it and
records `would_block` and an audit row. An event that cannot block allows and
records `would_block`. Observe mode never enforces, and Secure Client allows
and audits recovered errors regardless of its configured fail mode. A
standalone managed host is the exception: a recovered error gives no verdict,
so the call is blocked as when the gateway is down, in observe mode too and
whatever `hook_fail_mode` says, for every event that supports a block
response. A stop or session-end event is allowed there, because a block would
keep the agent running. The block
is a fail-closed answer without a policy finding. Treat
the condition as a degraded security incident: alert on the
`defenseclaw.panics.total` counter and on audit rows with result `panic`, and
inspect gateway health.

Ordered chains follow the same non-weakening rule. A SQLite timeout, closed
store, missing canonical session, or integrity conflict can prevent a new
chain match, but it cannot turn an independently blocked tool call into allow.
An exact unexpired deny receipt can replay its stable denial without emitting
duplicate finding telemetry.

## Persisted fail mode

Show current global and connector-effective values:

```bash
defenseclaw guardrail fail-mode
defenseclaw guardrail status
```

Set one connector closed:

```bash
defenseclaw guardrail fail-mode closed --connector codex --yes
defenseclaw guardrail fail-mode closed --connector claudecode --yes
```

Run bare, `guardrail fail-mode` prints the global value and each active
connector's effective value. On a Claude Code and Codex install with
`guardrail.hook_fail_mode: open`, after
`guardrail fail-mode closed --connector codex --yes`:

```text
  guardrail.hook_fail_mode: open

  per connector:
      - Claude Code (claudecode): open
      - Codex (codex): closed

  Invalid, unauthorized, incomplete, and unreachable gateway responses BLOCK connectors that are closed above.
  ! Still fail-open: claudecode. Close it with: defenseclaw guardrail fail-mode closed --connector <name>
  Switch to open:   defenseclaw guardrail fail-mode open
```

Claude Code shows `open` because it has no value of its own and the global
value is `open`; Codex shows `closed` because of its connector override.

Omitting `--connector` writes the broad posture. On a multi-connector install,
a broad write reconciles active connector overrides so an old per-connector
value cannot silently keep one peer on the prior mode.

The fail mode is written to `guardrail.hook_fail_mode` (or the connector's own
`hook_fail_mode`) in `config.yaml`, and it is also baked into the generated hook
scripts: each carries a `# defenseclaw-derived: sha256=... fail_mode=closed`
header. The scripts are derived files, so the command restarts the gateway by
default to render them again and reconcile native hook state. The key is
not one of the
[restart-required keys](/docs/reference/cli#restart-required-keys): with
`--no-restart` the running gateway still reloads the new mode and, with hook
self-heal on, renders the hook scripts again itself. `guardrail status` reports configured and runtime
values so that drift is visible, and `defenseclaw doctor` warns with `stale
generated script (... bakes hook fail mode open; config.yaml says closed)` and
names the command that renders the scripts again.

On a managed standalone host the administrator's config sets the fail mode;
change it there.

A connector turned off with `guardrail disable --connector X` has no hooks, so
it has no fail mode: `guardrail status` shows `-` in its Fail column and
`guardrail fail-mode` lists it as `disabled (no hooks)`.

Proxy-backed connectors have no hooks, so the hook fail mode does not apply to
them (see the [gateway outage table](/docs/connectors/capability-matrix#gateway-outage)); `guardrail fail-mode` lists them as
`closed (proxy-backed, no hooks ...)`.

## Connector response shapes

Fail mode can block only where the agent protocol has a block shape. A
closed failure returns the same block response a policy denial would, on the
events below:

| Connector | Events that can block | Native ask |
| --- | --- | --- |
| Claude Code | `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`, `Stop`, `SubagentStop`, `ConfigChange`, `PreCompact`, `Elicitation`, `ElicitationResult` | `PreToolUse` |
| Codex | `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `SubagentStop`, `PreCompact`, `PostCompact`, `Stop` | None |
| Cursor | `preToolUse`, `subagentStart`, `beforeShellExecution`, `beforeMCPExecution`, `beforeReadFile`, `beforeTabFileRead`, `beforeSubmitPrompt` | None |
| GitHub Copilot CLI | `preToolUse`, `permissionRequest`, `agentStop`, `subagentStop` | `preToolUse` |
| Devin | `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `Stop` | None |
| Antigravity | `PreToolUse` | `PreToolUse` |
| Hermes | `pre_tool_call` | None |
| OpenCode | `tool.execute.before` | None |
| OpenHands | `pre_tool_use`, `user_prompt_submit`, `stop` | None |
| Kiro | `UserPromptSubmit`, `PreToolUse` | None |
| Amp | `tool.call`, `tool.result` | `tool.call`, `tool.result` (foreground thread) |
| OmniGent | `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `AfterAgentResponse`, `BeforeModel`, `AfterModel` | `UserPromptSubmit`, `PreToolUse`, `BeforeModel` |

- An already-completed result event cannot undo its original side effect.
- An observation-only event remains observation-only even when fail mode is
  closed.

Whether a connector fails closed, and what an outage does on it per install
and fail mode, is in the [capability matrix](/docs/connectors/capability-matrix)
and its [gateway outage table](/docs/connectors/capability-matrix#gateway-outage). See the
[connector platform details](/docs/connectors#platform-support) before relying
on a specific event.

## Strict availability

`DEFENSECLAW_STRICT_AVAILABILITY=1` is an unconditional closed override for
transport and missing-token failures on the hooks that can block a call. It
exists for managed or compatibility deployments that must never open during
a gateway outage. It does not add a missing hook, convert native OTLP into
enforcement, or make an unsupported connector block-capable.

Not every hook reads it; the [gateway outage table](/docs/connectors/capability-matrix#gateway-outage) says which do. A
hook that does not read it uses the fail mode setup installed with it: run
`defenseclaw guardrail fail-mode closed` (on a managed host the administrator
sets `hook_fail_mode: closed`).

Because a strict outage can make the agent unavailable, use persisted status,
gateway monitoring, and a tested restart path before applying it broadly. On
native Windows, set normal posture with `guardrail fail-mode` so setup, doctor,
and status can reconcile and report it.

Administrator-managed hooks force the relevant unavailable-home and transport
failures closed rather than trusting a user-controlled process environment.

## The environment does not set the fail mode

A hook's fail mode is the one installed with it: the mode setup baked into
the shell hook or the OpenCode plugin, or the one in `hooks/.hookcfg` that the
native Windows hook reads. On a managed computer that is the administrator's
config, which only root or SYSTEM can change. Outside the Secure Client
shell hooks (below), nothing in the agent's environment changes it:
`DEFENSECLAW_FAIL_MODE` is not read, so `open` does not open a closed hook
and `closed` does not close an open one. A missing,
unreadable or malformed installed record is `closed`. To change the mode, run
`defenseclaw guardrail fail-mode open|closed`, which saves it in the config
and the installed hooks.

`defenseclaw status` and `defenseclaw doctor` read the same installed state,
so what they report is what the hooks do. A variable set in the shell that
runs them changes nothing. One exception: on a managed Windows computer the
native hook takes its mode from the runtime generation the guardian
publishes, which they cannot check. They show the administrator's mode with
the provenance and the drift `windows-managed-runtime-unverified`, never as
current, and doctor's Mode row warns instead of passing, also right after the
administrator changes the mode. `defenseclaw enterprise windows verify`, from
an elevated prompt, checks the runtime itself.

`DEFENSECLAW_STRICT_AVAILABILITY=1` is the one process setting the hooks
read. It can only close: on a hook that can block, it blocks a call while the
gateway is down, even when the hook is installed open. Not every hook reads
it (see the [gateway outage table](/docs/connectors/capability-matrix#gateway-outage)). Status still reports the installed mode.

Hooks rendered by 1.0.3 or earlier read `DEFENSECLAW_FAIL_MODE` until the
upgrade's connector refresh renders them again. Under an authenticated Secure
Client deployment, the shell hooks the [gateway outage table](/docs/connectors/capability-matrix#gateway-outage) marks
*Secure Client only* still take it as a full override (Secure Client delivery
is unchanged in 1.0.4).
Status and doctor cannot see the agent's environment, so they never report
such a hook as current: the provenance and the drift are
`agent-env-unverified`, and doctor's Mode row fails when the config asks for
`closed` (a warning under Secure Client). The one environment they can read is
Claude Code's settings `env`: `open` there is reported as the mode the hook
runs. Run `defenseclaw-gateway restart` to render the Claude Code and Codex
hooks again.

## Shared inspect scripts

The shared `inspect-*.sh` scripts serve every connector of one data
directory, and `DEFENSECLAW_CONNECTOR` only picks the connector they report
as. They run open only when every connector recorded there is open: one
connector set to `closed` closes them for all, also after an upgrade that
kept an older global `open`. A malformed or partial record (for example a
`fail_modes` value in `hooks/.hookcfg` that is not a map, or a
`hooks/.hookcfg.<connector>` file that names another connector) also closes
them, and so does a host with neither `jq` nor `python3`, where they cannot
read `hooks/.hookcfg` (Secure Client delivery is unchanged).

Environment keys are case-insensitive on Windows. Do not define multiple
case-variants with different values.

## Reporting and diagnosis

```bash
defenseclaw version
defenseclaw-gateway status
defenseclaw status
defenseclaw guardrail status      # configured and runtime fail mode per connector
defenseclaw guardrail fail-mode   # effective value per connector
defenseclaw doctor --passive      # no synthetic telemetry, LLM, or inspection probes
```

Hook delivery and response failures can also be recorded under
`$DEFENSECLAW_HOME/logs/hook-failures.jsonl`; on a packaged native Windows
install the pinned default is
`%USERPROFILE%\.defenseclaw\logs\hook-failures.jsonl`. Treat it as sensitive
operational data and do not publish the whole file.

A call that ran fail-open is never silent: the hook scripts, the native hook
and the OpenCode plugin each write a line to that file. A per-user gateway reads the
lines added to that file since its last start, and records one
`guardrail-degraded` alert (severity HIGH) per connector, for example
`2 hermes hook calls ran without a DefenseClaw check (fail-open) while the
gateway was unreachable or did not answer (first ..., last ...; last reason:
gateway unreachable)`. `defenseclaw alerts` lists it. Lines of fail-closed
calls (the agent showed the block) and lines older than 7 days are not
reported.

If doctor reports a missing token or token drift, preview its repair with
`defenseclaw doctor --fix --dry-run`. For how doctor repairs tokens, the audit
database, the device key, and observability circuits, see
[Doctor repair safety](/docs/reference/cli#doctor-repair-safety).

## Legacy connector fields

Fields such as `claude_code.fail_mode` and `codex.fail_mode` are legacy
policy-layer hints. Generated and native hook runtime behavior comes from
`guardrail.hook_fail_mode` and its per-connector entries. Use the guardrail
command and status output; do not hand-edit the legacy fields expecting runtime
behavior to change.
