## Is this for you?

- **One person, one computer: use the open-source install.** You own it and can
  change its policy or turn it off. Start with the [Quickstart](/docs/get-started/quickstart).
- **A fleet your IT team manages: use enterprise deployment.** An administrator
  or an MDM installs DefenseClaw as operating-system services. The people who
  run AI agents, and the agents themselves, cannot turn it off.
- **You need** an MDM, configuration-management tool or administrator shell
  that runs commands as SYSTEM on Windows and as root on Linux and macOS, and
  agents that run as standard users.

The [feature table](/docs/support-matrix#features) compares the editions. The
[enterprise route table](/docs/support-matrix#enterprise) lists which agents are
protected on which OS.

<Callout title="Ready to deploy?">
[Deploy to a fleet](/docs/enterprise/get-started) walks through six steps, from
choosing a profile to a ringed rollout.
</Callout>

In the config, enterprise deployment is `deployment_mode: managed_enterprise`
([definition](/docs/enterprise/concepts#managed_enterprise)).

## Two profiles

| Detail | Standalone | Secure Client |
| --- | --- | --- |
| Choose it when | You deploy with an MDM, a `.deb`, `.rpm` or `.pkg` package, configuration management or an administrator shell | You run Cisco Secure Client and want DefenseClaw as one of its modules |
| Platforms | Windows, Linux, macOS | Windows, macOS |
| Who decides on each tool call | The local policy engine (rule packs, policy, CodeGuard). Cisco AI Defense is added when you store an API key | Cisco AI Defense only. The local detectors are off |
| If Cisco AI Defense is unreachable | The local verdict stands | The Secure Client posture applies |
| Documented in | This section | [Secure Client managed deployment](/docs/enterprise/secure-client) |

- **One profile per computer.** Both profiles use the same gateway port, and on
  Windows the same service names. Uninstall one before you install the other.
- **The profile is fixed at install.** `enterprise.profile` in the config and
  `DEFENSECLAW_ENTERPRISE_PROFILE` in every service must agree, or the service
  refuses to start.
- **The default depends on the OS.** With neither set, Windows and macOS use
  `secure_client` and Linux uses `standalone`. Linux rejects `secure_client`.
  For a standalone deployment on Windows or macOS, set
  `enterprise.profile: standalone`.

The rest of this section covers the standalone profile.

## What runs where

Every endpoint runs four services and one program:

- The [gateway](/docs/enterprise/concepts#gateway) decides on each tool call.
- The [guardian](/docs/enterprise/concepts#guardian) installs and repairs each
  user's hooks.
- The [enumerator](/docs/enterprise/concepts#enumerator) finds the users to
  protect.
- The [sensor helper](/docs/enterprise/concepts#sensor-helper) answers a fixed
  set of privileged discovery questions for the gateway.
- The [hook](/docs/enterprise/concepts#hook) (`defenseclaw-hook`) is not a
  service. It is an administrator-owned program that the agent runs as the user.

The services and their identities:

| Part | Windows | Linux (systemd) | macOS (launchd) |
| --- | --- | --- | --- |
| Gateway | `DefenseClawGateway`, LocalSystem write-restricted by its `NT SERVICE\DefenseClawGateway` service SID | `defenseclaw-gateway.service`, as the `defenseclaw` user with no capabilities. systemd holds its sockets | `com.cisco.defenseclaw.gateway`, as the hidden `_defenseclaw` user |
| Guardian | `DefenseClawHookGuardian`, LocalSystem | `defenseclaw-hook-guardian.service`, root with a bounded capability set | `com.cisco.defenseclaw.hook-guardian`, root |
| Enumerator | `DefenseClawHookEnumerator`, LocalSystem | `defenseclaw-hook-enumerator.service`, root with a bounded capability set | `com.cisco.defenseclaw.hook-enumerator`, root |
| Sensor helper | `DefenseClawSensorHelper`, LocalSystem | `defenseclaw-sensor-helper.service`, root | `com.cisco.defenseclaw.sensor-helper`, root |
| Applies a config change | Your MDM runs `ensure` again | `defenseclaw-enterprise-apply.path` runs `ensure` when the config, secrets or policies change | `com.cisco.defenseclaw.apply` does the same |
| Daily check | Your MDM runs detection or `verify` | `defenseclaw-enterprise-verify.timer` | `com.cisco.defenseclaw.verify`, at 03:17 local time |

The guardian reconciles every minute and the enumerator runs every five
minutes. The gateway listens on `127.0.0.1:18970`. On Linux and macOS, hooks
and DefenseClaw's in-agent plugins reach it only through the hook socket,
`/run/defenseclaw-hook/hook.sock` on Linux and
`/opt/cisco/defenseclaw/run/hook.sock` on macOS. The kernel tells the gateway
each caller's uid, and there is no TCP fallback. On Windows they use loopback
with credentials bound to the user's SID.

The files in each zone, per OS, are in the [threat model](/docs/enterprise/threat-model#trust-zones)
and on the install pages: [Windows](/docs/enterprise/windows#layout),
[Linux](/docs/enterprise/linux#layout), [macOS](/docs/enterprise/macos#layout).

## Who can change what

| What | Administrator or MDM | DefenseClaw services | Standard user, and any agent they run |
| --- | --- | --- | --- |
| Config and policies, including thresholds and block and allow lists | Writes | The gateway reads them. The lifecycle is the only writer of `config.yaml` | No write. The local config tools refuse |
| Secrets | Writes | The gateway reads the one it needs | No access |
| Binaries and services | Installs, upgrades, removes | Run them | Runs the hook. Cannot stop, change or replace a service |
| Per-user hook config | Not needed | The guardian writes DefenseClaw's entries, as the user | Owns the files. The guardian repairs its entries, and the [foreign-hook guard](/docs/enterprise/foreign-hook-guard) handles hooks the user adds |
| Vendor machine policy | Writes. DefenseClaw changes only its own entries | The lifecycle or the guardian writes DefenseClaw's entries ([who writes it](/docs/enterprise/machine-policy#who-writes-machine-policy)) | The agent reads it. No write |
| Audit logs | Reads | The gateway writes them | No access |

An AI agent has exactly the rights of the user it runs as. DefenseClaw does not
defend a computer from its own administrators: an agent that runs with
unrestricted `sudo` or administrator rights is an administrator. The
[threat model](/docs/enterprise/threat-model#what-a-standard-user-cannot-do)
lists what a standard user cannot do and the risks that remain.

## Policy changes on a managed host

On a managed standalone host, `config.yaml` and the policy assets it names are
the only policy. Only the lifecycle (and a migration it runs) writes the config.
Under the Secure Client profile none of this applies. The model is in
[Configuration: one source of truth](/docs/reference/source-of-truth).

These attempts are refused, also for root, and write nothing:

| Attempt | Result |
| --- | --- |
| `defenseclaw config set KEY VALUE`, `config unset KEY` | Exit `3`: `error: This device is managed: change config.yaml in the admin config (MDM or management plane), not on the device` |
| `defenseclaw skill`, `mcp`, `plugin` or `tool` with `block`, `allow` or `unblock` | Exit `3`: `This device is managed: add it to asset_policy in the admin config (MDM or management plane)` |
| `defenseclaw init`, `defenseclaw quickstart`, and any command that needs a per-user config | Exit `3`: `This device is managed: DefenseClaw is configured by your administrator (MDM or management plane), so there is no per-user config to create and 'defenseclaw init' does not apply. Nothing was changed.` |
| `guardrail block-at`, `policy activate`, the `setup` commands that write config, the TUI config editor | Refused by the same writer. The TUI shows `Config save failed:` and the message |
| `POST` or `DELETE` on the gateway's `/enforce/block`, `POST` on `/enforce/allow` | HTTP `403` with `{"error": "managed_device", "detail": "policy changes are made in the management plane"}` |

The gateway records each refusal in the audit log with
`outcome=refused reason=managed_device`. On Linux and macOS the CLI reports
through the hook socket, so a standard user's refusal is recorded with the
account the kernel reports (`actor=uid:501 user=alice`). Windows has no hook
socket: only a refusal by an account that holds the gateway token is recorded.
The enterprise packages ship no `defenseclaw` CLI, so these commands matter
where a per-user install left one behind.

To block or allow an asset, add it to `asset_policy` in the admin config and
apply the config:

```yaml title="config.yaml (excerpt)"
asset_policy:
  skill:
    denied:
      - name: acme-unapproved-skill
        reason: not approved
```

- **Runtime actions stay allowed.** Quarantine and restore, runtime disable and
  enable, approvals (HITL) and discovery are runtime state, not policy.
- **The environment cannot weaken the host.** Every `DEFENSECLAW_*` variable
  has a `managed` setting in the [registry](/docs/reference/env-vars). `ignore`
  variables read as unset, from the process environment and from `.env` files.
  `tighten_only` variables (`DEFENSECLAW_FAIL_MODE`,
  `DEFENSECLAW_STRICT_AVAILABILITY`, `DEFENSECLAW_HOOK_MAX_BODY`) count only
  when they make the setting stricter. `allow` variables are read as set. A
  forged `DEFENSECLAW_DEPLOYMENT_MODE` or `DEFENSECLAW_ENTERPRISE_PROFILE`
  cannot make the host look local: the host is managed because `config.yaml`
  says so. `defenseclaw doctor` names ignored variables, never their values.
- **Local block and allow rows are ignored.** The gateway decides from
  `asset_policy`, not from the `actions` table of `audit.db`. When `ensure`
  migrates a config on a host that holds such rows, it adds the warning
  `local_enforcement_entries_ignored`.

## Supported platforms and agents

| OS | Requirements |
| --- | --- |
| Windows | 64-bit Windows on x64 (no ARM64 build). A machine-wide PowerShell 7 from Microsoft's installer. An elevated administrator or SYSTEM context |
| Linux | systemd 239 or later. `.deb` and `.rpm` packages for x86-64 and arm64, and a tarball. Run as root |
| macOS | macOS 13.0 or later on Apple silicon, for the `defenseclaw-enterprise-<version>-darwin-arm64.pkg` package. Run as root |

Details are under **Requirements** on each install page:
[Windows](/docs/enterprise/windows#requirements),
[Linux](/docs/enterprise/linux#requirements),
[macOS](/docs/enterprise/macos#requirements).

DefenseClaw protects each agent in one of two ways:

| Route | Agents |
| --- | --- |
| [Machine policy](/docs/enterprise/concepts#machine-policy-connector): hooks in the vendor's administrator-owned policy files | Claude Code, Codex, Cursor, GitHub Copilot, OpenCode (with DefenseClaw's managed plugin) |
| [Per-user](/docs/enterprise/concepts#per-user-connector): the guardian writes and repairs the hook in each enrolled user's config | Devin, Antigravity, Hermes, Amp, Kiro, and OpenCode while the managed plugin is not in force |

OpenClaw, ZeptoClaw and ACP editors are not supported in enterprise
deployments. The [support matrix](/docs/support-matrix#enterprise) lists the
verified agent and OS combinations, and each [connector page](/docs/connectors#platform-support)
lists agent versions.

## A minimal config

The administrator config is one YAML file. This one protects Codex and Claude
Code in observe mode, so policy verdicts do not block yet. With
`guardrail.rule_pack` unset, the gateway uses the rule packs built into it; for
your own, see [Custom rule packs](/docs/enterprise/configuration#custom-rule-packs).

<Tabs items={['Linux', 'macOS', 'Windows']}>
  <Tab value="Linux">

```yaml title="/etc/defenseclaw/config.yaml"
config_version: 9
deployment_mode: managed_enterprise
data_dir: /var/lib/defenseclaw          # must be exactly this path
policy_dir: /etc/defenseclaw/policies
enterprise:
  profile: standalone
gateway:
  api_bind: 127.0.0.1
  api_port: 18970
guardrail:
  enabled: true
  mode: observe                         # observe | action
  connectors:
    codex: {}
    claudecode: {}
```

  </Tab>
  <Tab value="macOS">

```yaml title="/opt/cisco/defenseclaw/etc/config.yaml"
config_version: 9
deployment_mode: managed_enterprise
data_dir: /opt/cisco/defenseclaw/runtime   # must be exactly this path
policy_dir: /opt/cisco/defenseclaw/etc/policies
enterprise:
  profile: standalone
gateway:
  api_bind: 127.0.0.1
  api_port: 18970
guardrail:
  enabled: true
  mode: observe                            # observe | action
  connectors:
    codex: {}
    claudecode: {}
```

  </Tab>
  <Tab value="Windows">

```yaml title="config.yaml (Windows)"
config_version: 9
deployment_mode: managed_enterprise
# Leave data_dir unset: the services use C:\ProgramData\Cisco\DefenseClaw\runtime.
enterprise:
  profile: standalone
gateway:
  api_bind: 127.0.0.1
  api_port: 18970
guardrail:
  enabled: true
  mode: observe                            # observe | action
  connectors:
    codex: {}
    claudecode: {}
```

  </Tab>
</Tabs>

- **Nothing is protected until you list agents.** Each key under
  `guardrail.connectors` turns on one agent. On Linux and macOS, the config the
  lifecycle writes when you supply none lists no agents. On Windows, install and
  `ensure` require a config. To leave a listed agent unprotected, set
  `enabled: false` or `ownership: "off"`. See
  [Choose the agents to protect](/docs/enterprise/configuration#choose-the-agents-to-protect).
- **Observe mode does not block on policy verdicts.** It records every decision,
  including what it would have blocked. Set `guardrail.mode: action` to enforce.
  The deployment's own checks apply in both modes: a tool call is refused while
  an unapproved foreign hook is present (with `foreign_hooks: remove`), or when
  the user is not enrolled where enrollment is enforced.
- **The data directory is fixed.** Linux and macOS reject any other `data_dir`.
  Windows rejects a `data_dir` other than the runtime directory.
- **Unusual layouts need enrollment hints (Linux and macOS).** Homes outside
  `/home`, `/var/home` or `/Users` go in `enterprise.enrollment.home_roots`.
  Agents installed under an administrator prefix go in
  `enterprise.enrollment.agent_prefixes`. See [Enrollment](/docs/enterprise/enrollment#home-roots-and-install-prefixes).

Where the file goes on each OS and every `enterprise.*` setting are in
[Configuration](/docs/enterprise/configuration). The optional Cisco AI Defense
key never goes in the config; store it as [Cisco AI Defense key](/docs/enterprise/ai-defense-key) shows.
