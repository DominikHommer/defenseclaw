A signed policy bundle is a `.dcbundle` file that carries a `config.yaml`, the policy
files it names, a manifest of their hashes and a detached signature. A managed
computer applies it only if a key in its trust anchor file signed it. Bundles
work on the standalone profile. A Secure Client computer refuses every `bundle`
command.

`sign` and `verify` run on any OS and change nothing. `verify` runs the device
checks only on the managed device, elevated. `status` reads the device and must run
as root or an elevated administrator. For delivery, see
[Install order with a signed bundle](/docs/enterprise/mdm#install-order-with-a-signed-bundle).

## Sign a bundle

```bash
defenseclaw-gateway enterprise bundle sign --in ./policy --out v12.dcbundle \
  --key signing.pem --key-id acme-2026a --tenant acme --device-group eng-laptops \
  --version 12 --created-by operator:alice --summary "Block HIGH for eng"
```

The key is a PEM Ed25519 or ECDSA P-256 private key. `--key-id` must name a key in
the devices' trust anchor file, and `--tenant` must equal the anchor's tenant.
`--platform` (repeatable) limits the targets; the default is Linux, macOS and
Windows.

Leave `data_dir` out of a managed bundle so each device uses its own service
directory.

`sign` prints errors, which refuse the bundle, and warnings, which it records in the
manifest. Use `--json` for a machine-readable result.

### Sign with an HSM or KMS

Write the unsigned bundle with `--emit-digest` in place of `--key`:

```bash
defenseclaw-gateway enterprise bundle sign --in ./policy --out v12.unsigned.dcbundle \
  --emit-digest --tbs-out v12.tbs --tenant acme --device-group eng-laptops \
  --version 12 --created-by operator:alice
```

What the HSM signs depends on the key type:

- **Ed25519:** the exact bytes in the `--tbs-out` file. Do not sign the printed
  digest: an Ed25519 signature over it does not verify.
- **ECDSA P-256:** the printed SHA-256 digest (`to_be_signed_sha256` in `--json`).

Then attach the signature (DER, raw `r||s` or base64). `--key-id` and `--public-key`
(the PEM public key) are required, and the signature must verify with that key:

```bash
defenseclaw-gateway enterprise bundle sign --attach-sig v12.sig \
  --in v12.unsigned.dcbundle --out v12.dcbundle \
  --key-id acme-2026a --public-key signing.pub.pem
```

## Verify a bundle

On a workstation or in CI, check against the anchor file you deliver:

```bash
defenseclaw-gateway enterprise bundle verify --bundle v12.dcbundle \
  --anchors bundle-anchors.json --platform linux
```

This checks the anchor, key, signature, manifest, tenant, device group, platform,
the anchor `min_version`, minimum product version, file hashes, inline secrets,
secret references, the config validator and the effective policy digest. It warns
`anchor_trust_unchecked`, since only a device needs a root-owned anchor file.

It cannot run the device checks: the installed anchor file, the version the device
last confirmed, and that each credential the bundle names is stored. A bundle that
passes on a workstation can still be refused by the device. For those checks, run
`verify` on the managed device as root or an elevated administrator:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise bundle verify --bundle v12.dcbundle
```

Without elevation, `verify` skips what it cannot read and warns `floor_unchecked` or
`secret_presence_unchecked`. On Windows it may not read the installed anchors at all.

### The version floor

A device accepts a bundle only if its version is above its floor. The floor is the
higher of two numbers: the `min_version` in the trust anchor file, and the version of
the last bundle the device confirmed. A bundle at or below the floor is refused
with `version_not_newer`, and the message says which of the two set the floor
(`floor_source` in the JSON: `trust_anchor_min_version`, `last_confirmed_bundle`,
`both` or `none`).

The bundle the device already runs (same ID, version and manifest) is a no-op
success. A different manifest under the same ID and version is refused. To roll
back, sign the old content again as a new, higher version with `--rollback-of`.

The confirmed floor is stored in a root-only state file in the lifecycle directory.
It never goes down while that file exists. On Linux and macOS a plain `uninstall`
removes that file, as does `--purge`; only `uninstall --keep-state` keeps it. So keep
`min_version` current in the anchor file you deliver: that part of the floor survives
a reinstall.

### Retired and revoked keys

Each key in the anchor file is `active`, `retired` or `revoked`.

| Status | Verifies |
| --- | --- |
| `active` | Any bundle it signed. |
| `retired` | Only the bundle the device already applied, so a repair can re-verify it after a key rotation. A new bundle signed by it is refused with `key_expired`. |
| `revoked` | Nothing. |

To rotate, add the new key as `active`, sign new bundles with it, and mark the old key
`retired` once devices have confirmed a bundle from the new one.

### Digest warnings

Each bundle records the effective policy digest the signer computed for every
platform, with the product version that computed it. The device recomputes it.

| Result | Meaning | What to do |
| --- | --- | --- |
| `digest_mismatch` (error) | The device runs the signer's product version and computes a different digest. The bundle is refused. | Fix the difference the message names, and sign again. |
| `digest_unverifiable` (warning) | The signer ran another product version, so the device cannot reproduce the digest. The bundle can still apply; the device reports its own digest. | Sign with the release the devices run. |
| `digest_layout_unverifiable` (warning) | The device uses a non-standard ProgramData root that changes its digest, and the signed digest matches the standard layout. | Use the standard layout, or accept the warning. |
| `secret_presence_unchecked` (warning) | The secret store could not be read, so `verify` did not check that the bundle's credentials are stored. | Run `verify` on the managed device as root or an elevated administrator. |

## Check a device

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise bundle status --json
```

On macOS the binary is `/opt/cisco/defenseclaw/bin/defenseclaw-gateway`. On Windows,
run `defenseclaw.exe enterprise bundle status --json` from an elevated prompt.

`status` shows the current (confirmed) bundle, the last good bundle kept for rollback,
the confirmed floor, the last receipt, the last refusal, whether sessions need a
restart, and whether the running gateway enforces the current bundle digest
(`applied`).

- The `floor` in `status` is only the stored confirmed floor. It leaves out the anchor
  `min_version`, so it can show `0` while an anchor `min_version` of 12 refuses
  version 12. For the effective floor and what set it, run `verify` on the device
  (`floor` and `floor_source` in its JSON), or read `min_version` in the anchor file.
- If the gateway cannot be asked, `status` adds the warning `gateway_unchecked` and
  leaves `applied` false. Run the platform's `enterprise status` for the gateway's
  own answer.
- The device keeps the 20 newest receipts. Older finished ones are removed.
- A standard user gets a privilege error and no state. The state files are root-only.

Exit codes follow the other lifecycle commands: `0` on success, `1` (Windows `1603`)
on a refusal, `2` (Windows `1639`) for invalid arguments.
