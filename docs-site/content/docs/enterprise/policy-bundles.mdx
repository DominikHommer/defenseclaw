A policy bundle is one signed file (`.dcbundle`) that carries `config.yaml`, the
policy files it names and a manifest with their SHA-256 hashes, the secret
references and the effective policy digest per platform. A detached signature
covers the manifest. The standalone enterprise profile only: Secure Client
computers do not have the `enterprise bundle` commands.

`sign` and `verify` run offline and change nothing on the computer; `apply`
installs a bundle on a managed Linux, macOS or Windows device. Your MDM
delivers the trust anchor file and the bundles
([Deliver with MDM](#deliver-with-mdm)) and detects the bundle that enforces
([Detection](#detection)). The [command reference](#command-reference) and the
[error and exit codes](#error-and-exit-codes) are at the end of the page.

## Install the trust anchor file

MDM installs `bundle-anchors.json` with the tenant, the device groups of the
device (empty: any group), the lowest bundle version it accepts
(`min_version`) and the signing public keys:

| OS | Path |
| --- | --- |
| Linux | `/etc/defenseclaw/trust/bundle-anchors.json` |
| macOS | `/opt/cisco/defenseclaw/etc/trust/bundle-anchors.json` |
| Windows | `C:\ProgramData\Cisco\DefenseClaw\etc\trust\bundle-anchors.json` |

On a managed device the file and every folder above it must be owned by root
(Windows: SYSTEM or Administrators) with no write access for other accounts and
no links. Otherwise verify refuses with `anchor_insecure`.

Each key has a `key_id`, an `alg` (`ed25519` or `ecdsa-p256-sha256`), a DER
SubjectPublicKeyInfo `public_key` in base64, `not_before` and `not_after` in UTC
and a `status`: `active`, `retired` (verifies only the bundle the device already
applied) or `revoked` (verifies nothing).

## Sign

```bash
defenseclaw-gateway enterprise bundle sign --in ./policy --out v12.dcbundle \
  --key signing.pem --key-id acme-2026a --tenant acme --device-group eng-laptops \
  --version 12 --created-by operator:alice
```

To sign with an HSM or KMS, run sign with `--emit-digest` (and `--tbs-out` for
an Ed25519 HSM that signs the message itself), sign the printed SHA-256, then
attach the signature:

```bash
defenseclaw-gateway enterprise bundle sign --attach-sig v12.sig --in v12-unsigned.dcbundle \
  --out v12.dcbundle --key-id acme-2026a --public-key acme-2026a.pub.pem
```

Sign refuses a literal secret anywhere in the bundle (`inline_secret`): name an
enterprise credential (`secret://NAME`) instead. Keep the signing key outside
the bundle directory.

## Verify

```bash
defenseclaw-gateway enterprise bundle verify --bundle v12.dcbundle --json
```

Verify checks, in order: the anchor file, the key, the signature, the manifest,
tenant and target, the version floor, `min_product_version`, the file hashes,
inline secrets, secret references (and on a managed device that each required
credential exists), the config and the effective policy digest. The first
failure is reported with a stable code and exit code 1 (1603 on Windows).

## Apply (Linux and macOS)

```bash
sudo defenseclaw-gateway enterprise bundle apply --bundle v12.dcbundle --json
```

Apply copies the bundle into the bundle store and verifies the copy (every
check of `verify`, the version floor and the credentials), then installs its
`config.yaml` with the ensure transaction. The policy in force keeps enforcing
until the gateway reports the policy of the new config, the new config
generation and no reload error; then the bundle becomes current in one atomic
write. If the gateway does not confirm it within 20 seconds the transaction
rolls back (`not_confirmed`) and the last good bundle enforces. A run that is
interrupted is recovered by the next lifecycle run. Applying the current bundle
again is a no-op (`noop_reason: already_applied`). The lifecycle result carries
the receipt in its `bundle` block; exit codes are 0, 1 (`errors[].code`), 75
(another run holds the lock) and 2 (usage).

MDM can also copy a bundle into `/etc/defenseclaw/bundles/inbox/` (macOS:
`/opt/cisco/defenseclaw/etc/bundles/inbox/`). The apply trigger applies the
highest version there and removes the processed files; `apply --inbox` does the
same on demand.

Once the trust anchor file is installed the device is in bundle mode: every
lifecycle run applies the config of the current bundle, an edit of
`config.yaml` in place is reverted, and `ensure --config` with any other config
is refused with `bundle_required`.

## Apply (Windows)

Run Setup elevated (or as SYSTEM from your MDM) on a computer where the
standalone deployment is installed:

```powershell
DefenseClawSetup-Enterprise-Standalone-x64.exe /ensure BUNDLE=C:\Stage\v12.dcbundle TRUSTANCHORS=C:\Stage\bundle-anchors.json JSON=1
```

`TRUSTANCHORS=` installs the anchor file into
`C:\ProgramData\Cisco\DefenseClaw\etc\trust\` first; give it on the first
bundle and whenever you rotate keys. It must sit in a folder only
administrators can change. `BUNDLE=` may come from any local folder: Setup
copies it into the bundle store under `C:\ProgramData\Cisco\DefenseClaw\etc\bundles\`
and verifies that copy. `BUNDLE=` is not combined with `CONFIG=` (the bundle
carries the config; exit code 1639), and neither is `TRUSTANCHORS=`: once
the anchors are installed the computer takes its policy only from signed
bundles. The ordinary ensure then installs the
bundle config, with the same transaction and rollback as `CONFIG=`. The bundle
becomes current only when the running gateway reports the effective policy of
the installed config with no reload error; otherwise Setup installs the last
good config again and the receipt fails (`not_confirmed`, `rolled_back: true`).
Exit codes are the MDM contract: 0, 1603 (`errors[].code`), 1618 (another
bundle run holds the store) and 1639.

On a confirmed bundle the marker key `HKLM\SOFTWARE\Cisco\DefenseClaw\Enterprise`
gains `BundleId`, `BundleVersion` and `BundleState=confirmed`. Detection:

```powershell
powershell -File detect.ps1 -RequireBundle 12
```

detects when the confirmed bundle is version 12 or newer (or exactly the
bundle id you give) and `enterprise bundle status` reports that the gateway
enforces it. The generic wrapper takes the same inputs:
`Invoke-DefenseClawEnterprise.ps1 -SetupPath ... -Sha256 ... -BundlePath ... -TrustAnchorPath ...`.
`defenseclaw.exe enterprise bundle apply --bundle <file>` runs the same ensure
from the installed CLI.

## Deliver with MDM

Deliver three things: the trust anchor file (once, and again when you rotate
keys), each signed bundle, and every credential a bundle names in
`secret_refs`, with the secret delivery you already use. A bundle never
carries a secret value.

| OS | Wrapper | Bundle | Trust anchor file |
| --- | --- | --- | --- |
| Linux, macOS | `packaging/mdm/linux` or `macos/defenseclaw-enterprise.sh` | `--bundle-file FILE`, or the base64 of the bundle in `dc_inline_bundle` | `--trust-anchor-file FILE`, or the JSON in `dc_inline_trust_anchors` |
| Windows | Setup `/ensure`, or `Invoke-DefenseClawEnterprise.ps1` | `BUNDLE=`, `-BundlePath` | `TRUSTANCHORS=`, `-TrustAnchorPath` |

```bash
sudo ./defenseclaw-enterprise.sh --trust-anchor-file /Library/Management/DefenseClaw/bundle-anchors.json \
  --bundle-file /Library/Management/DefenseClaw/v12.dcbundle
```

On Linux and macOS the wrapper runs, in this order: the package or payload
step when you give `--source`, the credential (`--secret-name` with
`--secret-file` or `--secret-stdin`), the trust anchor file, then
`enterprise bundle apply` on the wrapper's own copy of the bundle. It prints
the apply's lifecycle result and exits with its code (0, 1, 2 or 75; it
retries 75 twice).

- The anchor file is the root of trust, so its path must be root-owned and
  not writable by group or others, like `--config-file`. The wrapper writes it
  as root, mode 0644, to the path in [Install the trust anchor
  file](#install-the-trust-anchor-file). An identical file is left alone.
- The bundle may come from any folder: the apply verifies its own copy. It is
  at most 4 MiB.
- A bundle carries its config. `--bundle-file` (or an inline bundle) refuses
  `--config-file`, `--config-stdin` and a non-empty inline config with
  `mdm_invalid_arguments` (exit 2).
- When the apply fails, the bundle in force keeps enforcing and the wrapper
  puts back the anchor file it replaced, or removes the one it added. A bad
  anchor file never replaces the one that verified the bundle in force.
- `--trust-anchor-file` without a bundle installs the anchor file after the
  ensure. Use it to roll out a new key before the first bundle signed with it,
  and check the file on a workstation first with `bundle verify --anchors
  FILE --bundle <a bundle signed with the new key>`.
- The same delivery again is a no-op (`already_applied`), so the MDM can run
  the script on a schedule.

The wrapper applies its copy directly instead of dropping it into the inbox,
so its result and exit code are the bundle's. A package that only drops a
bundle into the inbox relies on the apply trigger; check the outcome with
[detection](#detection).

## Status

```bash
sudo defenseclaw-gateway enterprise bundle status --json
```

Status changes nothing. It reports bundle mode (whether the trust anchor file
is installed), the current and last good bundle, the version floor, the last
receipt (`received`, `verified`, `staged`, `applied`, `confirmed` or `failed`
with its error code and times) and whether the running gateway enforces the
effective policy digest of the current bundle. The enterprise status
(`--json`) of every platform carries the same summary in its `bundle` block. A bundle
that fails or whose run is interrupted never becomes current: the last good
bundle keeps enforcing, and the next lifecycle run ends an interrupted receipt
as `failed` with `interrupted`.

## Detection

| Question | Linux and macOS | Windows |
| --- | --- | --- |
| Is bundle 12 (or newer) enforcing? | `detect.sh --require-bundle 12` | `detect.ps1 -RequireBundle 12` |
| Is this exact bundle enforcing? | `detect.sh --require-bundle b-<ULID>` | `detect.ps1 -RequireBundle b-<ULID>` |
| What happened to the last delivery? | `detect.sh --bundle-status` | The marker values `BundleId`, `BundleVersion` and `BundleState`, and `enterprise bundle status --json` |

`--require-bundle` detects only when the current, confirmed bundle is that
bundle id, or that version or a newer one, and `enterprise bundle status`
reports that the running gateway enforces its effective policy digest. A
newer version counts, so an assignment for version 12 does not try to
reinstall over version 13. Otherwise the `value` and `jamf` formats print
`bundle-missing`, `bundle-mismatch`, `bundle-outdated` or
`bundle-not-enforced`, and the `exit` format exits 1 with the reason on
STDERR. The script-only setting is `DC_REQUIRE_BUNDLE`.

`--bundle-status` (setting `DC_BUNDLE_STATUS=1`) prints one line for the last
bundle receipt and always exits 0, inside `<result>` with `--format jamf`:

| Line | Meaning |
| --- | --- |
| `<bundle id> <version> confirmed` | The bundle enforces |
| `<bundle id> <version> not-enforced` | Confirmed, but the running gateway does not report its digest (stopped, or a reload was rejected) |
| `<bundle id> <version> failed:<code>` | The delivery failed with that [code](#error-and-exit-codes); the bundle before it keeps enforcing |
| `<bundle id> <version> received`, `verified`, `staged` or `applied` | A run is in progress or was interrupted; the next lifecycle run settles it |
| `none 0 none` | No bundle received yet |
| `none 0 not-installed`, `none 0 unknown` | No managed deployment; or not run as root, or the state could not be read |

Use it as a Jamf Pro extension attribute (data type String) or in a
compliance script that requires the line to end in ` confirmed`.

## Audit and telemetry

Every receipt that ends, `confirmed` or `failed`, is also written to the public
summary `<etc>/bundles/receipt.json` (mode 0644): the receipt id, bundle id,
version, signing key id, principal (`created_by`), change summary, state,
error code, effective and enforcing policy digests, config generation, the
times, `rolled_back`, `restart` and the bundle that enforces now. It never
carries a secret or the error message. The gateway of a standalone managed
device reads it within about 5 seconds and reports each terminal receipt once:

| Signal | What it carries |
|---|---|
| Log `config.bundle.receipt` (`compliance.activity`, outcome `applied` or `failed`) | `defenseclaw.policy.bundle.receipt_id`, `.state`, `.id`, `.version`, `.signer_key_id`, `.change_summary`, `.error_code`, `.rolled_back`, `.restart`, `.enforcing_digest`, `defenseclaw.policy.effective_digest`, `defenseclaw.config.generation`; the principal is `defenseclaw.admin.principal_ref` |
| Log `config.change.applied` | for a config a bundle installed: the bundle principal and `defenseclaw.policy.bundle.id`, `.version`, `.signer_key_id`, `.change_summary` |
| Counter `defenseclaw.policy.bundle.applies` | one per terminal receipt, labels `bundle.result` (`confirmed`, `failed`) and `bundle.error_code` |
| Gauge `defenseclaw.policy.bundle.version` | the version of the bundle the device enforces |
| `/health` and `/status` `policy` object | `bundle_id` and `bundle_version` of the config the live generation runs |

Both log events are control-plane records: they keep their mandatory floor
when a destination drops ordinary records. All of it is reporting only;
enforcement does not depend on it.

## Command reference

All four verbs are on `defenseclaw-gateway` (Windows: `defenseclaw.exe`) under
`enterprise bundle`. On a Secure Client computer every verb refuses with
`not_supported_secure_client` before it changes anything.

| Command | Flags | Notes |
| --- | --- | --- |
| `sign` | `--in DIR`, `--out FILE`, `--key PEM`, `--key-id ID`, `--tenant T`, `--device-group G`, `--version N`, `--created-by P`, `--parent ID`, `--rollback-of ID`, `--summary S`, `--min-product-version V`, `--platform linux\|darwin\|windows` (repeat; default all three), `--emit-digest`, `--tbs-out FILE`, `--attach-sig FILE`, `--public-key PEM`, `--json` | Offline, any OS, no root. Runs the whole validator, refuses errors and records warnings in the manifest. |
| `verify` | `--bundle FILE\|DIR`, `--anchors FILE` (default: the installed anchor file), `--platform P` (default: this OS), `--json` | Changes nothing. On a managed device as root it also checks the version floor and the credentials. |
| `apply` | `--bundle FILE\|DIR` or `--inbox`, `--reason R`, `--lock-wait D`, `--json` | Root or administrator, standalone managed device only. Prints the lifecycle result with the `bundle` block. |
| `status` | `--json` | Root or administrator. Changes nothing. |

## Error and exit codes

| Result | Linux and macOS | Windows |
| --- | --- | --- |
| Applied, or nothing to do (`already_applied`, `inbox_empty`) | `0` | `0` |
| Refused or failed; `errors[].code` names why | `1` | `1603` |
| Another run holds the lock (`lifecycle_busy`): retry later | `75` | `1618` |
| Invalid arguments | `2` | `1639` |

Retry only the busy code. A refused bundle keeps failing until you deliver a
different bundle, anchor file or credential.

| Code | Meaning | What to do |
| --- | --- | --- |
| `archive_invalid` | Not a well-formed bundle: over a size limit, a link, a bad or duplicate name, an unexpected top-level entry | Build it again with `bundle sign` |
| `manifest_invalid` | `manifest.json` or `manifest.sig` does not decode, or a field breaks its rule | Build it again with `bundle sign` |
| `anchor_missing`, `anchor_invalid` | No trust anchor file is installed, or it does not decode | Deliver a valid anchor file |
| `anchor_insecure` | The anchor file or a folder above it is writable by another account, or a link | Fix the owner and mode (Windows: the ACL) |
| `key_unknown`, `key_revoked`, `key_expired` | The signing key is not in the anchor file, is revoked, or is outside `not_before`..`not_after` (a retired key verifies only the bundle already applied) | Sign with an active key, or deliver an anchor file that has it |
| `signature_invalid` | The signature does not verify | Sign again; never edit a signed bundle |
| `tenant_mismatch`, `target_mismatch` | The bundle is for another tenant, device group or platform | Sign it for this device |
| `version_not_newer` | The version is at or below the floor (last confirmed version or `min_version`) | Sign a higher version; a rollback is a new version |
| `product_too_old` | The device runs an older product than `min_product_version` | Upgrade first |
| `file_missing`, `file_extra`, `file_hash_mismatch` | The content differs from `files[]` | Build it again with `bundle sign` |
| `inline_secret` | A file holds a literal secret | Use `secret://NAME` |
| `secret_ref_missing` | A required credential is not on the device | Deliver the credential first, then the bundle |
| `config_invalid` | The config fails validation | Fix the config and sign again |
| `digest_mismatch` | Same product version and platform as the signer, but another effective policy digest | Sign on the product version the devices run |
| `apply_failed` | The ensure transaction failed and rolled back; the lifecycle code is in `errors[]` too | Read the lifecycle code |
| `not_confirmed` | The gateway did not report the new policy in time; rolled back | Check `status` and the gateway log, then deliver again |
| `interrupted` | A run stopped before it finished; the next run settled it | Deliver again |
| `lifecycle_busy` | Another run holds the lock | Retry |
| `bundle_required` | `ensure --config` or `CONFIG=` on a device in bundle mode | Deliver a signed bundle |
| `bundle_state_unreadable`, `state_invalid` | The bundle state or the current version directory cannot be read | Deliver a bundle with a higher version; see the limits below |
| `bundle_inbox_refused` | An inbox file is not administrator-controlled | Copy it as root |
| `not_managed` | Not a standalone managed device | Install the enterprise profile first |
| `not_supported_secure_client` | A Secure Client computer | Bundles are standalone only |
| `mdm_anchor_install_failed` | The Linux or macOS wrapper could not write the anchor file, or its folder is not root-only | Fix the folder, then run again |

The MDM wrapper codes (`mdm_*`) and their exit codes are in
[Exit codes](/docs/enterprise/mdm#exit-codes).

## Known limits

- **Version floor.** A device refuses a version at or below the higher of
  `min_version` and its last confirmed bundle (`version_not_newer`), also a
  different manifest that reuses the confirmed bundle id and version. A
  rollback is a new, higher version with the old content. `bundle verify` run
  as root on a managed device also checks the last confirmed bundle; as a
  standard account it cannot read the bundle state, checks `min_version` only
  and warns `floor_unchecked`. The floor lives in the root-only
  `bundle-state.json`: a purge or reinstall that removes it starts again from
  `min_version`, so raise `min_version` in the anchor file as you retire old
  bundles.
- **Receipt telemetry timing.** The gateway reports a receipt when it next
  looks at `receipt.json` (about every 5 seconds), so the audit event can
  follow the lifecycle result by a few seconds. A gateway that is down when a
  receipt ends reports it when it starts. Only the last finished receipt is
  public: two receipts that end within one poll report the later one; the
  root-only receipts and `bundle status` keep all 20. The gateway records the
  key of the last receipt it reported in `bundle-receipt.reported` in its
  data directory; removing that file reports the current receipt once more.
- **Version gauge.** `defenseclaw.policy.bundle.version` is recorded when the
  gateway starts, when the bundle the live generation runs changes and with
  each receipt; between those it is not re-sent. A device that has never
  confirmed a bundle records none.
- **Principal in telemetry.** `created_by` is at most 256 bytes; sign and
  verify refuse a longer one. The OTel attribute
  `defenseclaw.admin.principal_ref` carries only letters, digits and
  `. _ : / -`, so a principal such as `control-plane:acme/alice@example.com`
  or `operator:CORP\admin` is left out of the attribute; the receipt,
  `receipt.json` and `config.generation.json` keep it.
- **Rollback record.** A failed apply that rolls back to the last good
  bundle records the restored config as that bundle again (its principal
  and bundle fields), so `/health` names the bundle that enforces. A
  rollback to a config no bundle installed is recorded as the lifecycle.
- **Windows restart path.** On Windows, a bundle config applied without a
  gateway restart is recorded as the bundle principal with the bundle fields.
  A bundle config that needs the restart path is installed by the upgrade
  transaction, so `config.change.applied` and `config.generation.json` name
  the lifecycle and not the bundle; the `config.bundle.receipt` event and the
  receipt still name the bundle and its principal.
- **Status needs root.** The bundle state and receipts are readable only by
  root or an administrator; `bundle status` as a standard account refuses with
  `not_root`. The device keeps the 20 newest receipts.
- **Retired and expired keys.** A retired key verifies only the bundle already
  applied, and only while the key is inside `not_before`..`not_after`. Once a
  key expires, the bundle it signed no longer verifies (`key_expired`): publish
  a bundle signed with the new key before the old one expires.
- **Effective policy digest.** Sign loads the config once, on the signing host.
  A device compares the manifest digest only when it runs the same product
  version on the same platform as the signer; otherwise verify warns
  `digest_unverifiable` and reports the digest the device computes. The file
  hashes are always checked.
- **Anchor file off a device.** `--anchors` on a computer that is not a managed
  device skips the ownership check (warning `anchor_trust_unchecked`), so an
  administrator can check a bundle on a workstation.
- **Secret presence.** When the enterprise secret store cannot be read (a
  standard account), verify warns `secret_presence_unchecked` instead of
  checking each credential.
- **Sizes.** A bundle is at most 4 MiB compressed, `manifest.sig` 16 KiB, the
  anchor file 64 KiB with at most 32 keys and 256 device groups.
- **Windows: install first.** Setup applies a bundle only on a computer
  where the standalone deployment is installed (`not_managed` otherwise):
  install with `/ensure CONFIG=<config.yaml>`, then deliver `BUNDLE=`. The
  first install cannot take a bundle yet.
- **Windows: confirm after commit.** The Windows transaction commits the
  bundle config before the gateway confirms it. Until then the gateway keeps
  enforcing its previous policy generation; a bundle that is not confirmed is
  replaced by the last good config in the same run (or, for the first
  bundle, by the config installed before it). A run that stops after the
  commit and before the confirm (an MDM timeout, a reboot) is settled by the
  next bundle run: the bundle becomes current when the gateway enforces its
  config, and otherwise its receipt fails `not_confirmed` while its config
  stays installed until the new bundle of that run (or a later one) replaces
  it. Windows has no bundle inbox:
  deliver each bundle with Setup or `bundle apply --bundle`.
- **Windows: credentials.** The wrapper stores `-SecretName` after the
  ensure, so a bundle that requires a credential the computer does not hold
  yet fails `secret_ref_missing`; store the credential first (a run with
  `-SecretName` only), then deliver the bundle.
- **Receipt digest.** The `effective_policy_digest` of a receipt and of
  `bundle status` is the digest the running gateway reports. It covers the
  install path of the bundle version directory, so it differs from the
  manifest digest even when verify compared that digest.
- **Restart-required keys.** A bundle that changes a key the gateway cannot
  reload restarts it (receipt `restart: true`); managed hooks fail closed for
  the few seconds of the restart.
- **Inbox files.** Only regular `*.dcbundle` files that only root can write are
  read; names that start with a dot are ignored, so copy under a dot name and
  rename. One run applies only the highest version there and removes every
  file it looked at, also one that was refused: the receipt of the highest
  version records the outcome, and a lower version in the same batch is
  removed without a receipt, even when the highest one is refused. Drop one
  bundle at a time.
- **First bundle after a crash.** When a run dies after it installed the first
  bundle but before it recorded it, and the gateway then does not report its
  policy, there is no last good bundle to return to: the receipt fails
  `not_confirmed` and the gateway keeps enforcing the policy it last built.
  Its version directory stays as long as the installed config names it.
- **Damaged version directory.** If the version directory of the current
  bundle is missing or no longer matches its confirmed manifest,
  changing runs refuse to apply any config (`bundle_state_unreadable`) and the
  installed config keeps enforcing. Applying the current bundle again does not
  repair it; apply a bundle with a higher version.
- **Root is trusted.** The checks protect a device from standard accounts
  and from tampered or replayed deliveries, not from its administrators: root
  (Windows: an administrator or SYSTEM) can replace the anchor file, edit the
  bundle state or remove DefenseClaw. A reinstall or purge that removes
  `bundle-state.json` resets the floor to the anchor's `min_version`; raise
  `min_version` as you retire old bundles.
- **MDM script size.** A bundle pasted into the wrapper as base64 grows by a
  third. MDMs limit script bodies (Intune for macOS: 1 MB per script), so keep
  an inline bundle well under that, and deliver a larger bundle as a file
  (`--bundle-file`) in a package. Bundles themselves are at most 4 MiB.
- **Wrapper runs that stop.** An MDM timeout that ends the Linux or macOS
  wrapper after it installed a new anchor file, and before the apply ended,
  leaves the new anchor file in place; the bundle in force keeps enforcing and
  the next delivery settles it. An anchor file delivered without a bundle is
  not checked until the next bundle applies.
- **Detection needs root.** `detect.sh` reads `enterprise bundle status`,
  which only root can run; under another account `--bundle-status` prints
  `none 0 unknown` and `--require-bundle` reports `bundle-missing`. Windows
  has no `--bundle-status` line; read the marker values instead.
