Roll out the [standalone profile](/docs/enterprise/plan/concepts#standalone-profile)
to a large, mixed fleet, for example 5,000 Windows, Linux and macOS endpoints.
This page says what to decide and in which order. The install pages and the MDM
recipes have the commands.

## Before you start

| Need | Details |
| --- | --- |
| Administrator rights | Your MDM must run commands as SYSTEM on Windows and as root on Linux and macOS |
| PowerShell 7 on Windows | A stable, machine-wide PowerShell 7 from Microsoft's installer. Deploy it first ([Windows requirements](/docs/enterprise/install/windows#requirements)) |
| systemd on Linux | systemd 239 or later and a `.deb` or `.rpm` distribution ([Linux requirements](/docs/enterprise/install/linux#requirements)) |
| Apple silicon on macOS | macOS 13.0 or later ([macOS requirements](/docs/enterprise/install/macos#requirements)) |
| Supported agents | A version the [connector page](/docs/connectors#platform-support) supports, installed for each user who runs it |
| Cisco AI Defense key (optional) | Only if you want Cisco AI Defense to inspect as well ([key](/docs/enterprise/configure/ai-defense-key)) |

The release files for each OS, with `checksums.txt` and `checksums.txt.bundle`:

| OS | Files |
| --- | --- |
| Windows | `DefenseClawSetup-Enterprise-Standalone-x64.exe`. `DefenseClawSetup-Enterprise-x64.exe` is the Secure Client Setup. `...payload-manifest.json` is published for auditing and is not delivered |
| Linux | `defenseclaw-enterprise-<version>-linux-<arch>.deb`, `.rpm` or `.tar.gz`, and when the release signs them, the `.asc` signatures and `defenseclaw-enterprise-release-key.asc` |
| macOS | `defenseclaw-enterprise-<version>-darwin-arm64.pkg` |

The MDM scripts that wrap these files are in `packaging/mdm`;
[Install with an MDM](/docs/enterprise/mdm) explains them.

<Callout type="warn" title="Agents with administrator rights">
DefenseClaw does not defend a computer from its administrators. An agent that
runs with unrestricted `sudo` or administrator rights can remove it. Keep
agents on standard accounts.
</Callout>

### Where releases come from

One workflow publishes every release: the Release workflow of the DefenseClaw
repository, run on `main`. It signs `checksums.txt` with cosign (a keyless
signature, stored as `checksums.txt.bundle`) under the identity
`https://github.com/cisco-ai-defense/defenseclaw/.github/workflows/release.yaml@refs/heads/main`
and the issuer `https://token.actions.githubusercontent.com`. The installers and
`defenseclaw upgrade` compile that identity in, and no config key or environment
variable changes it.

- `update.source` in the config (`https://` only), and its deprecated alias
  `DEFENSECLAW_REPO`, change only where release bytes are fetched. A mirror must
  serve the same signed `checksums.txt` and `checksums.txt.bundle` and the same
  files, unchanged. The tools refuse a mirror without cosign 2.0 or later.
- The checksum-only fallback exists only for the official source (`update.source`
  empty and `DEFENSECLAW_REPO` unset).
- Managed hosts do not update themselves. `defenseclaw upgrade` and
  `defenseclaw rollback` refuse, the update notice is off, and `DEFENSECLAW_REPO`
  is ignored. Your MDM delivers each release, pinned by its SHA-256 from a
  `checksums.txt` that you verified with cosign once
  ([hash-pinned trust](/docs/enterprise/mdm#what-you-deliver)).

## Step 1: Choose the agents

List every agent to protect under `guardrail.connectors`. Each key turns that
agent on. On Linux and macOS, the config the lifecycle writes when you supply
none lists no agents, so it protects nothing. On Windows, install and `ensure`
require a config.

```yaml title="config.yaml (excerpt)"
guardrail:
  enabled: true
  mode: observe
  connectors:
    codex: {}
    claudecode: {}
    cursor: {}
    copilot: {}
```

| Agents | How | Notes |
| --- | --- | --- |
| Codex, Claude Code, Cursor, GitHub Copilot, OpenCode | [Machine policy](/docs/enterprise/plan/concepts#machine-policy-connector) | Applies to every user of the computer. OpenCode uses DefenseClaw's managed plugin |
| Devin, Antigravity, Hermes, Amp | [Per-user](/docs/enterprise/plan/concepts#per-user-connector) | The guardian writes and repairs each enrolled user's config |
| Kiro | Per-user | The guardian writes each user's global `~/.kiro/hooks` file |

Machine-policy agents give the strongest protection: users cannot edit the
vendor's policy files, and where DefenseClaw sets the
[managed-hooks-only lock](/docs/enterprise/plan/concepts#managed-hooks-only-lock),
the agent ignores hooks users add. [Machine policy](/docs/enterprise/configure/machine-policy)
shows the lock per OS. [Choose the agents to protect](/docs/enterprise/configure/configuration#choose-the-agents-to-protect)
has the full rules.

## Step 2: Choose the users

The [enumerator](/docs/enterprise/plan/concepts#enumerator) enrolls a user for an
agent only after it finds a supported install of that agent for that user, and
it checks every five minutes. By default it picks interactive local and
directory users on Linux and macOS, and every interactive profile on Windows.
Narrow the set with `enterprise.enrollment`: `include_users`, `exclude_users`,
the group filters and `exempt_users`. Settings behave a little differently per
OS ([What each OS honors](/docs/enterprise/configure/enrollment#what-each-os-honors)).

- **Linux directory accounts.** SSSD and Active Directory often map users to
  IDs above 60000. The `UID_MAX` cap does not apply to them. Set `uid_max` only
  to cap directory and local accounts alike. Check an ID with `id -u <user>`.
- **One config for several OSes.** Windows applies `include_groups` and
  `exclude_groups` too. A Linux group name such as `wheel` does not resolve on
  Windows, so a new Windows user that no other entry admits stays pending and
  its machine-policy calls are refused. Name groups that exist everywhere (or
  use SIDs on Windows), or use separate configs.
- **Windows exclusions.** Excluding a Windows user does not leave them
  unprotected: their calls through a machine-policy agent are refused. Exclude
  only accounts that do not run protected agents. To keep an account working
  without per-user registrations, list it in `exempt_users`: it is inspected and
  logged.

## Step 3: Pilot in observe mode

Pick a pilot ring of about 50 endpoints that covers every OS, every chosen
agent and some IT staff. Deploy with `guardrail.mode: observe`. Policy verdicts
never block in observe mode, but the deployment's own checks still apply: a tool
call is refused while an unapproved foreign hook is present (with
`foreign_hooks: remove`), or when the user is not enrolled where enrollment is
enforced.

1. **Install.** Run the MDM recipe for each OS. Success is `0` everywhere. The
   failure codes are `1`, `2` and `75` on Linux and macOS and `1603`, `1618` and
   `1639` on Windows ([Exit codes](/docs/enterprise/mdm#exit-codes)).
2. **Check health.** Run `status` and `verify` on a few hosts and read
   `coverage_complete` and `security_complete`
   ([Status and verify](/docs/enterprise/operate/operations#status-and-verify)).
3. **Check enrollment.** Confirm the expected users appear for each per-user
   agent. Allow a few minutes after a user first installs an agent. A
   machine-policy-only Linux or macOS deployment can show an empty Enrollment
   section while its users are protected.
4. **Read the decisions.** Let people work for a week or two, review what
   DefenseClaw would have blocked ([Logs and events](/docs/enterprise/operate/operations#logs-and-events)),
   and tune policy for legitimate work it flags.
5. **Switch to action mode.** Set `guardrail.mode: action` and deliver the
   config again, or set `mode: action` under one agent's `guardrail.connectors`
   entry first ([Change the config](/docs/enterprise/operate/lifecycle#change-the-config)).

## Step 4: Handle existing per-user installs

On a managed computer, the per-user installer (`install.sh`, `install.ps1`),
`defenseclaw upgrade` and the per-user gateway refuse to run. DefenseClaw does
not migrate per-user installs, and `enterprise.coexistence.per_user_install` is
reserved: it is accepted and has no effect. Remove them before the managed
install reaches a computer:

1. Find them: a per-user install lives in `~/.defenseclaw`
   (`%USERPROFILE%\.defenseclaw` on Windows), with programs in `~/.local/bin`.
2. As that user, remove it. This keeps the user's data:

   ```bash
   defenseclaw uninstall --binaries --yes
   ```

   To remove the data too, add `--all`. On Windows always use
   `--all --binaries --yes`: Setup refuses a `%USERPROFILE%\.defenseclaw` folder
   a per-user install left.
3. Deploy the managed install.

A per-user gateway listens on the managed gateway's port, `127.0.0.1:18970`. If
one still holds it, the managed install on Linux and macOS stops before it
changes anything with `api_port_held`, naming the process. Stop that gateway or
move it to another port, then run `ensure` again.

On Linux and macOS, `--adopt-existing` covers a different case: DefenseClaw files
at the managed paths that no deployment owns, such as an earlier manual
deployment. `install` and `ensure` refuse to run over them unless you pass
`--adopt-existing`, which archives them into the lifecycle directory. It does not
touch per-user installs ([Linux](/docs/enterprise/install/linux#per-user-installs)).

## Step 5: Expand in rings

Move on only when a ring is healthy. A plan for 5,000 endpoints:

| Ring | Endpoints | Mode | Move on when |
| --- | --- | --- | --- |
| Pilot | About 50 (1%), every OS and agent | `observe` | Every install exits `0`, `verify` passes, and the decisions are reviewed |
| Early | About 500 (10%) | `observe`, then `action` | No unexpected blocks for a week in `action` mode |
| Broad | About 2,000 (40%) | `action` | Detection and health stay green |
| Everyone | The rest | `action` | |

Watch these on every ring:

- **MDM detection**, which reports the installed version and optionally health
  ([Detection](/docs/enterprise/mdm#detection)).
- **`coverage_complete` and `security_complete`** in the lifecycle result
  ([Health fields](/docs/enterprise/operate/operations#health-fields)).
- **Enrollment counts** for per-user agents against the users you expect.
- **The effective policy digest.** On Linux and macOS, `policy.effective_digest`
  should match on every host of one OS that got the same config, and
  `policy.applied` should be `true`
  ([digest](/docs/enterprise/operate/operations#effective-policy-digest-and-config-generation)).

On Linux computers that run Tetragon, the kernel controls follow the same rings:
`observe` on the pilot, then `enforce` ring by ring after burn-in
([Tetragon on a Linux fleet](/docs/enterprise/runtime/tetragon#step-4-approve-and-enforce-ring-by-ring)).

Two Windows cases keep `security_complete` at `false` on a healthy install.
Every other `false` needs a look.

- A Windows deployment needs at least one of Codex, Claude Code or Cursor turned
  on. One that protects only per-user agents or GitHub Copilot reports `false`.
- With Claude Code on, `security_complete` stays `false` until an administrator
  confirms in a real Claude Code session that the managed policy is in effect and
  records it with `repair --attest-claude-effective-policy`
  ([Verify the install](/docs/enterprise/install/windows#verify-the-install)).

## Step 6: Plan upgrades and rollback

Run `ensure` with the new release on the pilot ring first. On Linux and macOS the
package manager, or `ensure` with a newer payload, upgrades in place. On Windows,
`ensure` with the new Setup upgrades and refuses an older version over a newer
one. An upgrade keeps the administrator config. `ensure` migrates an older
`config_version` and keeps a backup (`config.yaml.v8.bak`, `migration-v9.json`;
[details](/docs/enterprise/operate/lifecycle#what-ensure-does-with-the-config)). Check
the record on the pilot ring before you widen it.
