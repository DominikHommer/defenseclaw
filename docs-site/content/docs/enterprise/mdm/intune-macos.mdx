<Callout title="Validation">A test tenant delivered DefenseClaw to an enrolled Mac with this script route, with a signed policy bundle, in the PR #1304 end-to-end pass: install, hot-applied bundle updates, an offline period and a one-time uninstall.</Callout>

You upload one root shell script: your copy of
`packaging/mdm/macos/defenseclaw-enterprise.sh` with its settings block and
config filled in. Every day it downloads
`defenseclaw-enterprise-<version>-darwin-arm64.pkg` from your HTTPS host,
installs it when the version differs, and runs `ensure`. A custom attribute from
`detect.sh` with `DC_FORMAT="value"` reports the installed version,
`not-installed`, `outdated` or `unhealthy`. Removal is a root shell script with
`packaging/mdm/macos/uninstall.sh`.

This recipe follows the [MDM contract](/docs/enterprise/mdm); read it first for
exit codes, detection and logs.

## Before you start

- **Tenant**: the Apple push certificate, device groups and licences are in place
  and the Macs are enrolled; see [Prepare your Intune tenant](/docs/enterprise/mdm/intune-tenant).
- **Macs**: Apple silicon on macOS 13.0 or later. The package refuses other hosts;
  its identifier is `com.cisco.defenseclaw.enterprise`.
- **Intune**: the Microsoft Intune management agent for macOS, which Intune
  installs when you assign a shell script. Intune runs macOS shell scripts only
  over a direct internet connection, not through a proxy, and stops a script after
  60 minutes.
- **Release**: verify `checksums.txt` and read the pkg's SHA-256 pin, as in
  [What you deliver](/docs/enterprise/mdm#what-you-deliver).
- **Config**: write the config as in
  [Configuration](/docs/enterprise/settings). Keep the AI
  Defense key out of it.

## Choose a route

| Route | Install | Detect | Use it when |
| --- | --- | --- | --- |
| **A. Shell script** (recommended) | One root shell script: the kit's wrapper with its settings block filled in | Custom attribute that runs `detect.sh`, and the script's own run status | Always, unless you must use app assignments |
| **B. macOS app (PKG)** | Intune's unmanaged PKG app type with the pkg | Unreliable: see below | You need Intune's app workflow for other reasons |

Intune's **macOS app (PKG)** type reports success from the app bundles listed under
**Included apps**. This package installs command-line binaries in
`/opt/cisco/defenseclaw/bin` and no `.app` bundle, so Intune can report a working
install as failed. Route A detects through the lifecycle instead.

## Route A: one root shell script

### 1. Host the package

Put the pkg on an HTTPS location the Macs reach without a proxy, for example an
Azure Blob Storage container or your artifact server. Use a direct HTTPS file URL:
the wrapper does not follow redirects, so a GitHub release link fails with HTTP 302. If the download needs a proxy, set `DC_HTTPS_PROXY` in the next step; only the
download uses it.

### 2. Fill in the wrapper's settings block

Copy `packaging/mdm/macos/defenseclaw-enterprise.sh` and edit the settings block at
the top of your copy. Intune runs the script with no arguments, so every value
goes here:

```sh
DC_ACTION=ensure
DC_SOURCE_URL="https://downloads.example.com/defenseclaw/defenseclaw-enterprise-<version>-darwin-arm64.pkg"
DC_SOURCE_SHA256="replace-with-the-64-hex-sha256-from-checksums.txt"
DC_TRUST_MODE=hash_pinned
DC_PRODUCT_VERSION="X.Y.Z"
```

For Developer ID trust on a signed and notarized pkg, set `DC_TRUST_MODE=signed`
and `DC_ALLOWED_TEAM_IDS` to the signer's Team ID. The wrapper then checks the
Developer ID Installer signature, the Team ID and Gatekeeper's notarization
verdict, and still checks `DC_SOURCE_SHA256` when you set it.

For an inline config, paste it between the `DEFENSECLAW_CONFIG` markers in
`dc_inline_config`. This minimal config protects Claude Code and Codex in observe
mode; build yours from
[Choose the agents to protect](/docs/enterprise/configuration#choose-the-agents-to-protect):

```sh
dc_inline_config() {
    cat <<'DEFENSECLAW_CONFIG'
config_version: 9
deployment_mode: managed_enterprise
data_dir: /opt/cisco/defenseclaw/runtime
policy_dir: /opt/cisco/defenseclaw/etc/policies
enterprise:
  profile: standalone
gateway:
  api_bind: 127.0.0.1
  api_port: 18970
guardrail:
  enabled: true
  mode: observe
  connectors:
    claudecode: {}
    codex: {}
ai_discovery:
  enabled: true
DEFENSECLAW_CONFIG
}
```

An inline `data_dir` must be exactly `/opt/cisco/defenseclaw/runtime`; omit it from
bundle config. Never put the AI Defense key in the script: Intune scripts are not
secret storage. For a signed bundle, paste the base64 bundle into
`dc_inline_bundle` or set `DC_BUNDLE_FILE`, and supply the trust anchors with
`DC_TRUST_ANCHOR_FILE`, `dc_inline_trust_anchors`, or an installed anchor file. The
bundle carries its own config; see
[Install order with a signed bundle](/docs/enterprise/mdm#install-order-with-a-signed-bundle).
On macOS the base config's rule pack lives in a root-owned folder you install
first, for example `/Library/Application Support/DefenseClaw-RulePacks/<pack>`.

### 3. Add the script in Intune

Go to **Devices** > **By platform** > **macOS** > **Manage devices** > **Scripts** >
**Add**:

| Setting | Value |
| --- | --- |
| Upload script | Your edited copy; the wrapper is about 30 KB. One tenant accepted and its Mac agent executed a 1,100,000-byte script; the maximum was not measured. |
| Run script as signed-in user | **No** (runs as root) |
| Hide script notifications on devices | **Yes** |
| Script frequency | **Every 1 day**. `ensure` changes nothing when the Mac already matches, but with `DC_SOURCE_URL` set every run downloads the pkg before it compares versions. Scripts with a frequency also run after a restart. |
| Max number of times to retry if script fails | **3**. Exit `75` means another run or the installer was busy, and a later run succeeds. |

Assign it to device groups. On each run the wrapper downloads the pkg, verifies it,
installs it only when its version differs from the installed one, applies the
inline config or signed bundle, and exits with the lifecycle's code. The script's
run status in Intune is Success for exit `0` and Failed otherwise. A version 8
inline config migration warning names **MDM inline config** as its source.

### 4. Report the version with a custom attribute

Copy `packaging/mdm/macos/detect.sh` and set `DC_FORMAT="value"` in its settings
block. Optionally set `DC_MIN_VERSION="X.Y.Z"` to report `outdated` below that
version, and `DC_REQUIRE_HEALTHY=1` to run `verify` and report `unhealthy` when it
fails.

Go to **Devices** > **By platform** > **macOS** > **Organize devices** >
**Custom attributes for macOS** > **Add**, set **Data type of attribute** to
**String**, and upload your copy. Intune runs custom attribute scripts about every
8 hours. `detect.sh` must run as root: it asks the installed, root-owned gateway
for its status, and reports `not-installed` otherwise. The pkg receipt is the other
inventory signal: `pkgutil --pkg-info com.cisco.defenseclaw.enterprise` prints
`version: X.Y.Z`. A pkg whose post-install step failed records no receipt, even
after `ensure --from-package` finishes the install, so install the pkg again once
you fix the cause.

## Route B: macOS app (PKG)

Add the pkg in **Apps** > **All Apps** > **Create** > **macOS app (PKG)**. The pkg's
post-install step runs `enterprise macos ensure --from-package`, and a failure
fails the install. It uses the config already at
`/opt/cisco/defenseclaw/etc/config.yaml`, or the built-in default, which protects
no agents. So:

- Set **Ignore app version** to **No**.
- Deliver the config with the Route A script, with `DC_SOURCE_URL` empty. On a Mac
  where the pkg is installed, that run applies the config. Where it is not yet
  installed, it fails with `mdm_not_installed` and succeeds on a later run.
- Track the result with the Route A custom attribute, not the app's install status.
- Keep any Intune pre-install script under 15,360 characters. Intune does not
  report post-install script failures.

## Deliver the Cisco AI Defense key

Intune scripts and custom attributes are not secret storage. After DefenseClaw is
installed, deliver the key once through an administrator channel, such as a remote
shell or a secrets agent that runs as root. First make sure the config turns the
feature on; see [Cisco AI Defense key](/docs/enterprise/ai-defense-key).

```bash
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise secret set \
  --name ai-defense-api-key --from-file /var/root/ai-defense.key
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise secret status
```

Or, from tooling that can drop a root-only file, run the wrapper with
`--secret-name ai-defense-api-key --secret-file /path/to/root-only-file`. Delete the
source file afterwards. Storing the key re-runs `ensure`, which applies it.

## Entra users and groups

With Platform SSO (the Microsoft Enterprise SSO plug-in in Company Portal), Entra
users sign in at the macOS login window, and the standalone profile records a
registered account as directory `entra_id` with its UPN, so a `users` assignment by
UPN works. Platform SSO puts no Entra group into the macOS group database, so a
`groups` assignment that names an Entra group matches no one until a local group
carries the membership. The settings catalog policy used live, the bridge script
and the measured results are in
[Deploy with Microsoft Entra ID](/docs/enterprise/identity-entra-id#4-macos-platform-sso).
Delivering the bridge script through Intune was not tested.

## Change the config, upgrade and roll back

- **Change the config**: edit the config in your script and save it. Intune runs
  the new version, and `ensure` validates and applies it. An invalid config fails
  the run with `config_invalid` and leaves the installed config unchanged.
- **Upgrade**: host the new pkg, then update `DC_SOURCE_URL`, `DC_SOURCE_SHA256`
  and `DC_PRODUCT_VERSION` in the script.
- **Roll back**: see [Roll back](/docs/enterprise/lifecycle#roll-back).

## Privacy prompts

The guardian writes per-user hook registrations in each user's home
dot-directories, such as `~/.claude` and `~/.codex`. macOS privacy protections
(TCC) do not cover those folders, so no Privacy Preferences Policy Control (PPPC)
profile is needed. If your organization moves agent configuration into protected
folders such as Desktop, Documents or iCloud Drive, deploy a PPPC profile that
grants **SystemPolicyAllFiles** to `/opt/cisco/defenseclaw/bin/defenseclaw-gateway`,
identified by its code requirement (`codesign -dr - /opt/cisco/defenseclaw/bin/defenseclaw-gateway`
prints it). This works only for a Developer ID-signed release: an unsigned
release's code requirement changes with every release.

## Deliver a custom macOS rule pack

Before the first pkg install, add a root **stage-pack** script that copies the pack
into `/opt/cisco/defenseclaw/etc/policies/guardrail/<name>` with `root:wheel`
ownership, `0755` directories and `0644` files. Use the
[stage-pack script and pin example](/docs/enterprise/mdm#stage-a-custom-macos-rule-pack),
and run it before the config and pkg steps. In `config.yaml`, set
`guardrail.rule_pack` to the pack name and `guardrail.custom_packs.<name>` to that
absolute path and its `sha256:<digest>` pin. Stage the pack again before
reinstalling after a purge.

## Remove DefenseClaw

First remove the Macs from the install script's assignment. The Intune agent for
macOS keeps running a cached recurring install script after its assignment is
removed. In the test tenant, Graph confirmed the install script had no
assignments, yet the Mac ran it 4 seconds later, and again 16 minutes later after
a full 15-minute check-in. So waiting one check-in is not enough, and a cached
install run after the uninstall reinstalls the pkg. Before you assign uninstall:

1. Check the Intune agent log on each Mac (`/Library/Logs/Microsoft/Intune`) and
   wait until each Mac has checked in and the install script's policy ID has stopped
   appearing.
2. Assign the uninstall script as a **new** script object. A run-once script that
   already ran on a Mac does not run again when you reassign it.
3. After the uninstall, check again at the next check-ins that
   `pkgutil --pkg-info com.cisco.defenseclaw.enterprise` finds no package. If a
   cached install run reinstalled DefenseClaw, run the uninstall again with another
   new script object.

Deleting the install script instead of unassigning it was not tested. The uninstall
is a root shell script set to run once, with `packaging/mdm/macos/uninstall.sh`; set
`DC_PURGE=1` in its settings block for a purge. What it removes is in
[Uninstall](/docs/enterprise/mdm#uninstall). On a Mac with nothing installed it
exits `0`.

## Troubleshoot

| Where | What |
| --- | --- |
| **Scripts** > your script > **Device status** | Intune's run status per Mac (Success for exit `0`) |
| `/Library/Logs/Microsoft/Intune` | The Intune agent's logs, including script runs |
| `/Library/Logs/Cisco/DefenseClaw/mdm-wrapper.log` | Install and ensure results (root, `0600`); uninstall removes this log, so use the Intune script output for its result |
| `/opt/cisco/defenseclaw/lifecycle/last-package-result.json` | The pkg's own `ensure` result |
| `/Library/Logs/Cisco/DefenseClaw/lifecycle.log`, `verify.log` | Config-change runs and the daily `verify` |

```bash
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos status --json
```
