<Callout title="Validation">A test tenant delivered the rule-pack app, the base Win32 app, signed bundle apps and the uninstall to an enrolled Windows device in the PR #1304 end-to-end pass. Intune supersedence of a base app that a bundle app depends on failed (`0x87D300DB`) and is unsupported. The kit's reference rule-pack scripts have not run in a tenant yet.</Callout>

You upload:

- a base Win32 app, `Install-DefenseClawIntune.intunewin`, that
  `New-DefenseClawIntunePackage.ps1` builds from
  `DefenseClawSetup-Enterprise-Standalone-x64.exe` and your `config.yaml`;
- one dependent Win32 app per signed bundle;
- a PowerShell 7 Win32 app;
- a rule-pack Win32 app, when the config names a custom rule pack.

The app runs `Install-DefenseClawIntune.ps1` as System, which runs Setup
`/ensure`. Base detection is the registry value `ProductVersion` under
`HKEY_LOCAL_MACHINE\SOFTWARE\Cisco\DefenseClaw\Enterprise`, greater than or equal
to the version you deploy. The bundle app uses a generated `detect-bundle.ps1`
that requires a confirmed bundle and an enforcing gateway. Uninstall runs
`Install-DefenseClawIntune.ps1 -Uninstall`, which runs Setup `/uninstall JSON=1`.

This recipe follows the [MDM contract](/docs/enterprise/mdm); read it first for
exit codes, detection and logs. The Intune Management Extension is a 32-bit
process, and install commands, detection scripts and Remediations run in Windows
PowerShell 5.1. So every Intune-facing script in the kit
(`packaging/mdm/intune/windows`) is 5.1-compatible and does two things: it reads
the enterprise marker through the 64-bit registry view, and it starts the native
x64 Setup or the installed `defenseclaw.exe`. The lifecycle runs in the trusted
PowerShell 7, never inside the Intune host.

## Before you start

- **Tenant**: licences, automatic enrollment and device groups are in place; see
  [Prepare your Intune tenant](/docs/enterprise/mdm/intune-tenant).
- **Devices**: Windows 10 or 11 x64 enrolled in Intune. The lifecycle refuses
  ARM64 and 32-bit Windows. Intune cannot enroll Windows Server.
- **WDAC/AppLocker**: allow or sign the DefenseClaw launcher, detection and
  Remediations scripts so they run in `FullLanguage`. Under
  `ConstrainedLanguage` they stop before calling Setup or checking health:
  install reports failure and detection reports not detected.
- **Release**: download `DefenseClawSetup-Enterprise-Standalone-x64.exe`, verify
  `checksums.txt` with cosign and read the Setup's SHA-256 pin, as in
  [What you deliver](/docs/enterprise/mdm#what-you-deliver).
- **Config**: write `config.yaml` as in
  [Configuration](/docs/enterprise/settings). Keep the AI
  Defense key out of it. Set `ai_discovery.enabled: true` if you expect
  `agent ide-plugins` to report installed AI extensions.
- **Workstation**: PowerShell 7.4 or later and Microsoft's `IntuneWinAppUtil.exe`
  (the Win32 Content Prep Tool).
- **Remediations** (optional) need Windows Enterprise E3 or E5, Education A3 or
  A5, or Windows VDA per-user licenses.

## 1. Add PowerShell 7 as a Win32 app

The lifecycle runs only in PowerShell 7 from Microsoft's x64 MSI, which registers
the engine under `HKLM\SOFTWARE\Microsoft\PowerShellCore\InstalledVersions` and
installs it in `C:\Program Files\PowerShell\7`. Preview builds are refused. Wrap
the MSI with `IntuneWinAppUtil.exe` and add it in **Apps** > **All Apps** >
**Create** > **Windows app (Win32)**:

| Setting | Value |
| --- | --- |
| Content | `PowerShell-7.x.y-win-x64.msi` from Microsoft, hash-checked |
| Install command | `msiexec /i PowerShell-7.x.y-win-x64.msi /qn ADD_PATH=1 USE_MU=1 ENABLE_MU=1` |
| Uninstall command | `msiexec /x {product-code} /qn` |
| Install behavior | **System** |
| Detection rule | **File**. Path `C:\Program Files\PowerShell\7`, file `pwsh.exe`, detection method **String (version)**, operator **Greater than or equal to**, value `7.4.0`, *Associated with a 32-bit app on 64-bit clients*: **No** |

## 2. Build the Win32 app content

On the administrator workstation, in PowerShell 7, run the kit's packager:

```powershell
./New-DefenseClawIntunePackage.ps1 `
  -SetupPath .\DefenseClawSetup-Enterprise-Standalone-x64.exe `
  -Sha256 '<SHA-256 of the Setup from checksums.txt>' `
  -ConfigPath .\config.yaml `
  -OutputDirectory .\intune-defenseclaw-<version> `
  -IntuneWinAppUtil C:\Tools\IntuneWinAppUtil.exe `
  -ProductVersion X.Y.Z
```

| Parameter | Meaning |
| --- | --- |
| `-SetupPath` | The Setup. Required. |
| `-Sha256` | The Setup's pin. Required with hash-pinned trust; the script refuses a Setup that does not match. |
| `-TrustMode` | `HashPinned` (default) or `Authenticode`. |
| `-AllowedSigners` | With `Authenticode`: SHA-256 thumbprints of accepted signer certificates, comma-separated or repeated. |
| `-ConfigPath` | The base config. It must select the same guardrail pack and rules as the signed bundle. Without a config the first install fails with `1639`. |
| `-BaseConfigPath` | Required for a bundle package: the exact base app config. Packaging refuses a missing base config, a `guardrail:` block that differs from the bundle's in more than the pack path, and a `claude_code:`, `codex:`, `connector_hooks:` or `application_protection:` block that differs from the bundle's. |
| `-BundlePath`, `-TrustAnchorPath`, `-RequireBundle` | For a bundle app: signed bundle, optional public anchors and required bundle version for detection. |
| `-OutputDirectory` | Where to write. Required. Its `content` folder must not exist yet. |
| `-IntuneWinAppUtil` | Path to `IntuneWinAppUtil.exe`. When set, the script also builds the `.intunewin`. |
| `-ProductVersion` | The release version. The script prints it in the detection rule and records it. |

The packager requires a `config_version: 9` config and refuses an inline
`api_key`. The base config must be plain ASCII with LF or CRLF line endings (no
tab, lone CR or non-ASCII byte, even in a comment; one UTF-8 byte order mark is
allowed). It also refuses a top-level key that is not plain lowercase (a tag,
anchor, escape or `?` key) and a quoted value or `{...}` or `[...]` that
continues on the next line. With `-BundlePath`, the compared blocks are the ones
listed for `-BaseConfigPath`; leave a hook mode block out of both or copy it from
the bundle.

The script verifies the Setup against `-Sha256` (and, for Authenticode, its
signer); writes `content\` with the Setup, `config.yaml`,
`Install-DefenseClawIntune.ps1` and `intune-package.json` (the SHA-256 pins
`setup_sha256` and `config_sha256`, the trust mode and the allowed signers); wraps
`content\` into `Install-DefenseClawIntune.intunewin`; and prints the values to
enter in the admin center.

### Signed bundle after the base install

Setup needs `CONFIG=` on first install and accepts `BUNDLE=` only after that. The
base config must select the same custom rule pack, digest, thresholds and rule
settings as the signed bundle, so the device enforces the bundle's rules from the
first install. Deliver three apps, in this order:

1. **Rule-pack app.** It installs the pack in an administrator-only folder the
   gateway service can read; see [Custom rule pack app](#custom-rule-pack-app).
2. **Base app**, built with `-ConfigPath`. Its config names the installed
   absolute pack path. Make the rule-pack app a dependency with **Automatically
   install: Yes**. The packager prints a `Prerequisite` line for every pack the
   config names outside the DefenseClaw install folders.
3. **Bundle app**, built with `-BundlePath` and the same base config, with the
   base app as its dependency (**Automatically install: Yes**). Upload the
   generated `detect-bundle.ps1` as its custom detection rule.

Until the bundle app installs, the computer enforces the base app's policy. The
packager compares only the `guardrail:` block (apart from each custom pack's path)
and the `claude_code:`, `codex:`, `connector_hooks:` and `application_protection:`
blocks. No other setting is compared. Copy every other enforcement setting the
bundle sets, such as `asset_policy:`, into the base config too, or the base app
can allow what the bundle blocks until the bundle installs. See
[Install order with a signed bundle](/docs/enterprise/mdm#install-order-with-a-signed-bundle).

```powershell
./New-DefenseClawIntunePackage.ps1 `
  -SetupPath .\DefenseClawSetup-Enterprise-Standalone-x64.exe `
  -Sha256 '<SHA-256 of Setup>' -BundlePath .\policy.dcbundle `
  -TrustAnchorPath .\bundle-anchors.json -RequireBundle 1 `
  -BaseConfigPath .\config.yaml -OutputDirectory .\intune-bundle-1
```

Verify the bundle offline first with the release the devices run. A device on the
signer's product version refuses a bundle whose signed Windows digest it computes
differently (`digest_mismatch`), whatever OS signed it, and
`enterprise bundle verify --platform windows` shows the same result offline. A
base-only device is installed but has no confirmed signed bundle; until the
bundle applies it enforces the base config's pack. With an empty or weaker base
pack, that interval can allow calls the bundle denies, which is why the packager
refuses a base config whose guardrail policy differs from the bundle's.

### Custom rule pack app

The kit's `Install-DefenseClawRulePack.ps1` and `Detect-DefenseClawRulePack.ps1`
are a reference rule-pack app. They are Windows PowerShell 5.1 scripts, so Intune
runs them as they are. The install script copies the pack folder to
`C:\ProgramData\DefenseClaw-RulePacks\<pack>` (or `-PacksRoot`), then sets what
Setup checks:

- on the parent folder: owner Administrators, no inherited entries, Full control
  for SYSTEM and Administrators, Read & execute for
  `NT SERVICE\DefenseClawGateway`, no `Users` or `Authenticated Users` entry;
- on the pack and everything in it: the same entries, owner Administrators.

`-PacksRoot` must be a folder of its own, because the install replaces its owner
and permissions. The script refuses (`1639`) a drive root, a Windows, program,
profile or DefenseClaw folder such as `C:\ProgramData` or `C:\Windows`, an
existing non-empty folder it did not set up, and one that holds anything other
than rule pack folders. It writes a `.defenseclaw-rule-packs` file in the folder,
and also accepts a folder that already has the permissions above, for example one
set up by hand from the [Windows guide](/docs/enterprise/windows#2-write-the-config).

The script sets the parent folder's permissions with `Set-Acl`, by SID. The app
runs before the base app, so the gateway service does not exist yet, and `icacls`
cannot grant its SID until it does (it fails with `1332`). It then checks the
copy and the permissions of the pack, its parent and every folder above, and
exits `0`. Run again, it changes nothing when everything is in place and repairs
only what differs; a changed pack is copied beside the old one and swapped in. It
exits `1603` with the problem when a check fails, and `1639` for invalid
arguments.

1. On the workstation, put the reviewed pack folder (its name is the
   `guardrail.custom_packs` name) next to the two scripts in a content folder, and
   print the pack's tree SHA-256 and the commands the install runs, without
   changing anything:

   ```powershell
   .\Install-DefenseClawRulePack.ps1 -PackName my-pack -PlanOnly
   ```

2. In your copy of `Detect-DefenseClawRulePack.ps1`, set the defaults of
   `$PackName` and `$ExpectedTreeSha256` (and `$PacksRoot` if you changed it).
   Intune runs detection scripts without arguments.
3. Wrap the content folder with `IntuneWinAppUtil.exe` (setup file
   `Install-DefenseClawRulePack.ps1`) and create the Win32 app:

| Setting | Value |
| --- | --- |
| Install command | `%SystemRoot%\Sysnative\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File .\Install-DefenseClawRulePack.ps1 -PackName my-pack -ExpectedTreeSha256 <tree sha256>` |
| Uninstall command | The same with `-Remove` instead of `-ExpectedTreeSha256 <tree sha256>` |
| Install behavior | **System** |
| Return codes | Keep the defaults; `1603` and `1639` report Failed |
| Detection rules | **Use a custom detection script**: your `Detect-DefenseClawRulePack.ps1`, *Run script as 32-bit process on 64-bit clients*: **No**, *Enforce script signature check and run script silently*: **No** (or **Yes** after you sign the script) |
| Assignments | The same device groups as the base app; the base app's dependency installs it first |

The detection script reports the pack installed only when the folder has the
expected tree SHA-256, only SYSTEM and Administrators own and can change it and
its parent, no standard user can read them, and the gateway service can read
them. Otherwise Intune runs the install command again, which repairs it. The
pack's digest in the config (`guardrail.custom_packs.<pack>.digest`) still pins
its files for the gateway.

If you deliver the pack another way, for example a pinned HTTPS download, it needs
the same permissions. When the gateway cannot read the pack folder or its parent,
Setup refuses the base app with `1639` and prints an `icacls` fix that names
`NT SERVICE\DefenseClawGateway`. `icacls` cannot resolve that name before the
first install (`1332`), so on a new device set the parent folder from an elevated
prompt with `Set-Acl`, then retry the base app:

```powershell
$Packs = 'C:\ProgramData\DefenseClaw-RulePacks'
$Acl = Get-Acl -LiteralPath $Packs
$Acl.SetSecurityDescriptorSddlForm('O:BAD:PAI(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)(A;OICI;0x1200a9;;;S-1-5-80-1858176940-1394861675-2895326486-505287571-2610476274)', 'Owner, Access')
Set-Acl -LiteralPath $Packs -AclObject $Acl
icacls "$Packs\my-pack" /reset /T /C
```

## 3. Create the Win32 app

Upload the `.intunewin` in **Apps** > **All Apps** > **Create** >
**Windows app (Win32)**:

| Step | Setting | Value |
| --- | --- | --- |
| Program | Installer type | **Command line** |
| Program | Install command | `%SystemRoot%\Sysnative\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File .\Install-DefenseClawIntune.ps1` |
| Program | Uninstall command | `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File .\Install-DefenseClawIntune.ps1 -Uninstall` |
| Program | Installation time required | 60 minutes (the default) |
| Program | Allow available uninstall | **No** |
| Program | Install behavior | **System** |
| Program | Device restart behavior | **Determine behavior based on return codes** |
| Program | Return codes | Keep the defaults: `0` Success, `1707` Success, `3010` Soft reboot, `1641` Hard reboot, `1618` Retry. The lifecycle's `1603` and `1639` then report as Failed. |
| Requirements | Operating system architecture | **x64** only |
| Requirements | Minimum operating system | The oldest Windows release your fleet runs. The packager prints Windows 10 22H2 as a starting point. DefenseClaw does not check the Windows version; it needs x64 and PowerShell 7. |
| Detection rules | Rule | **Registry**. Key path `HKEY_LOCAL_MACHINE\SOFTWARE\Cisco\DefenseClaw\Enterprise`, value name `ProductVersion`, detection method **Version comparison**, operator **Greater than or equal to**, value `<version>`, *Associated with a 32-bit app on 64-bit clients*: **No** |
| Dependencies | App | The PowerShell 7 app, **Automatically install**: **Yes** |
| Supersedence | Previous DefenseClaw app | Do not use with a dependent bundle app; see [Upgrade](#6-change-the-config-upgrade-and-roll-back). |
| Assignments | Required | Device groups |

Why these values:

- **The launcher.** Setup refuses relative and environment-expanded paths, and
  the Intune content folder is not known in advance.
  `Install-DefenseClawIntune.ps1` re-checks the pins in `intune-package.json`,
  builds the absolute `CONFIG=` path, runs
  `DefenseClawSetup-Enterprise-Standalone-x64.exe /ensure JSON=1 CONFIG=...`
  (adding `ALLOWEDSIGNERS=` for Authenticode), prints the result document and
  exits with Setup's code. A tampered or incomplete package fails with
  `mdm_hash_mismatch` or `mdm_package_incomplete` (`1603`).
- **`Sysnative`** starts the 64-bit Windows PowerShell from the 32-bit Intune
  host, as Microsoft recommends for 64-bit installs.
- **The uninstall command** names `powershell.exe` and the launcher without a
  path, because Intune does not expand environment variables in uninstall
  commands. The launcher re-checks the Setup pin and runs
  `DefenseClawSetup-Enterprise-Standalone-x64.exe /uninstall JSON=1` (`-Purge`
  adds `PURGE=1`). Setup refuses an uninstall with `uninstall_in_use`, before it
  changes anything, while a program runs from
  `C:\Program Files\Cisco\DefenseClaw\bin` (often an Intune detection or
  Remediations script that runs the installed CLI for a few seconds). With
  `-Purge`, Setup also refuses while a program has a file in
  `C:\ProgramData\Cisco\DefenseClaw` open, for example a SIEM forwarder reading
  `runtime\audit.db`. The launcher runs Setup again, at most 6 times, each after
  the named programs exit or 20 seconds pass. If Setup still refuses, the
  launcher exits `1618`, which Intune retries, and its result names each program,
  its process id and account. An app whose uninstall command is Setup itself
  fails such an uninstall with `1603` and is not retried. The kit's detection and
  Remediations scripts start no installed CLI while a lifecycle run holds the
  lock.
- **Version comparison, greater than or equal to.** A newer installed version
  still counts as installed, so an older app never tries to replace it.
- **Bundle detection.** The base registry rule proves only that Setup ran. Use the
  bundle app's generated detector to check signed policy enforcement.

If you prefer a script, `packaging/mdm/windows/detect.ps1` works as a custom
detection script. Intune runs detection scripts without arguments, so set the
default of `$MinimumVersion` in your copy's `param()` block to the app's version.
It reads the 64-bit registry view, so the **Run script as 32-bit process on
64-bit clients** setting does not matter.

## 4. Keep it healthy with Remediations

A Remediations package re-checks the deployment on a schedule and repairs it from
the installed payload. Create it in **Devices** > **Manage devices** >
**Scripts and remediations** > **Create script package**:

| Setting | Value |
| --- | --- |
| Detection script file | `Remediate-Detect.ps1` |
| Remediation script file | `Remediate-Fix.ps1` |
| Run this script using the logged-on credentials | **No** (runs as SYSTEM) |
| Enforce script signature check | **No**, or **Yes** after you sign both scripts with a certificate in the devices' Trusted Publishers store. With **Yes**, the scripts run under the device's PowerShell execution policy (Windows clients default to `Restricted`, so set `AllSigned` or `RemoteSigned`) and must be saved as UTF-8 without a byte-order mark. |
| Run script in 64-bit PowerShell | **No** (the default). The scripts work in either. |
| Schedule | **Daily**, or **Hourly** every 4 to 8 hours |

If you assign the package with Microsoft Graph, read the assignment back: Graph
can accept `runRemediationScript: true` and store `false`, and scheduled runs
then only detect. When it reads `false`, turn on the remediation script for that
assignment in the admin center. An on-demand run (**Run remediation** on the
device, or Graph `initiateOnDemandProactiveRemediation`) runs both scripts either
way.

`Remediate-Detect.ps1` runs the installed CLI's
`enterprise windows verify --profile standalone --json`. It exits `0` on a
healthy host, on a host without the deployment (installing is the Win32 app's
job), and while another lifecycle run holds the lock. Otherwise it exits `1` and
starts the remediation. Its one line names the failing check: each DefenseClaw
service that is not running with its start mode, or else the first error. On a
computer that takes signed policy bundles, healthy also means the running gateway
enforces the confirmed bundle: the script asks `enterprise bundle status --json`
and is compliant only when it names the marker's bundle as current with
`applied: true`. A `config.yaml` changed outside the lifecycle or deleted, or a
gateway that enforces another policy, is not compliant. Verify fails with
`bundle_not_applied`, and the line reads:

```text
verify failed (bundle_not_applied): config.yaml is not the config of signed policy bundle <id> version <n>
```

If the installed CLI's verify passes but the gateway enforces another policy,
`bundle status` catches it:

```text
signed policy bundle <id> version <n> is confirmed but not applied: the gateway enforces sha256:..., not sha256:...; the remediation re-applies it from the bundle store
```

A healthy line names the policy source:

```text
healthy; signed policy bundle <id> version <n> is applied (the gateway enforces it)
```

The line says instead that the installed config enforces when no bundle is
confirmed. Remediations do not install a missing bundle; the bundle app's
detection does.

`Remediate-Fix.ps1` first checks the same way. When the only problem is a stopped
or disabled hook guardian or enumerator while the gateway runs, it sets that
service back to automatic start, starts it and verifies again without touching
the gateway. (On a computer that takes signed bundles that fast path also needs
`bundle status` to report the bundle applied.) Otherwise it runs
`enterprise windows ensure --profile standalone --json`, which verifies and
repairs from the installed payload, or does nothing. A repair stops every
DefenseClaw service, so the gateway is down for one to two minutes and hooks fail
closed meanwhile. It exits with the lifecycle's code. After an upgrade that a
restart or power loss cut off, the installed (older) CLI rolls the change back:
the line says `repaired (recovered_pending_transaction): ensure rolled back an
interrupted lifecycle change`, names the release that runs again, and asks you to
run the newer Setup `/ensure` again (the Win32 app retries it).

On a computer that takes signed policy bundles, `ensure` first puts the confirmed
bundle's config back when `config.yaml` is not that config or is missing. It
renders the config from the verified, read-only version directory in the bundle
store (nothing comes from the network), writes it with the lifecycle writer, keeps
an edited file as `C:\ProgramData\Cisco\DefenseClaw\etc\rejected-config.yaml`
(administrators only), and reloads the running gateway, or restarts it when it
does not adopt the bundle. The result warns `bundle_config_restored`. While an
install transaction is pending, `ensure` recovers it first and warns
`bundle_restore_deferred`; it fails with `bundle_not_applied` while `config.yaml`
is still not the bundle's config, and the next run re-applies the bundle. Then
`Remediate-Fix.ps1` checks again that the gateway enforces the bundle, and only
then exits `0`:

```text
DefenseClaw <version>: repaired (bundle_config_restored): config.yaml was not the config of signed policy bundle <id> version <n>; ensure re-applied the bundle from the bundle store; signed policy bundle <id> version <n> is applied
```

When the bundle store cannot give the config back (a damaged version directory,
for example), nothing is started on the edited file and Intune shows the
remediation as failed:

```text
DefenseClaw <version>: still failing (bundle_restore_failed): signed policy bundle <id> version <n> is confirmed, but its config cannot be read from the bundle store (<reason>), so the device cannot prove it enforces it; deliver the bundle again or a newer one
```

Both scripts print one short line, because Intune keeps 2,048 characters of
output. The full result is in `%WINDIR%\Logs\DefenseClaw\enterprise-lifecycle.log`.
Remediations cannot install, upgrade or change the config; the Win32 app does
those. Nor can they put back a missing scanner runtime (one an antivirus
quarantined from `C:\ProgramData\Cisco\DefenseClaw-ScannerRuntime`, say):
`Remediate-Fix.ps1` exits `1603`, reports `scanner_runtime_unavailable` and names
Setup `/repair`. Deploy `DefenseClawSetup-Enterprise-Standalone-x64.exe /repair JSON=1`
from the Win32 app content, as a second Win32 app or a platform script that runs
as SYSTEM.

A missing hook binary is the same case. If an antivirus quarantines
`C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw-hook.exe`, Claude Code treats
the hook that cannot start as a non-blocking error and runs the tool call until
the file is back, which is a fail-open window. The hook guardian checks for the
file every 5 seconds and restores it from its protected copy, and Setup `/ensure`
and `/repair` restore it from their payload. Exclude
`C:\Program Files\Cisco\DefenseClaw\bin` from quarantine in your EDR policy so
the window does not open.

On a computer installed from the unsigned Setup, the Remediations `ensure` keeps
the marker's `hash_pinned` trust mode, so `detect.ps1`, `uninstall.ps1` and later
runs keep accepting the unsigned CLI.

## 5. Deliver the Cisco AI Defense key

Keep the key out of the Win32 app, `config.yaml` and every Intune script. First
make sure the config turns the feature on and names the credential; see
[Cisco AI Defense key](/docs/enterprise/ai-defense-key). After the Win32 app has
installed DefenseClaw, store the key from an elevated PowerShell 7 session on the
device, for example through your remote-support tool:

```powershell
$cli = 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe'
$key = Read-Host -AsSecureString -Prompt 'Cisco AI Defense API key'
ConvertFrom-SecureString -SecureString $key -AsPlainText | & $cli enterprise secret set --name ai-defense-api-key --from-stdin
& $cli enterprise secret status
```

The key goes from the prompt to the CLI's standard input and never touches the
disk, a command line or a script. To automate it, have your secrets-management
agent write the key to a file that only SYSTEM and Administrators can change, on
a local NTFS drive, run the command below as SYSTEM or an elevated administrator,
then delete the file:

```powershell
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise secret set --name ai-defense-api-key --from-file C:\ProgramData\YourAgent\ai-defense.key
```

The command runs only elevated and only when a standalone deployment is installed
(otherwise it exits `1603`); it refuses a file a non-administrator can change and
an invalid name or value (exit `1639`); and it writes
`C:\ProgramData\Cisco\DefenseClaw\secrets\ai-defense-api-key`, readable by SYSTEM,
Administrators and the gateway service, then restarts the gateway service.
`enterprise secret status` shows whether the key is present, when it changed and a
digest prefix, never the value. The wrapper options `-SecretName` with
`-SecretPath` or `-SecretFromStdin` do the same in tools that run PowerShell 7.

## 6. Change the config, upgrade and roll back

**Custom rule pack before the first install.** If `guardrail.rule_pack` selects a
`guardrail.custom_packs` entry, deliver its digest-pinned files with a
[rule-pack app](#custom-rule-pack-app) before the base Win32 app, and make the
rule-pack app a dependency of the install, upgrade and config apps. Avoid
embedding a large encoded pack in a platform script: Defender can block it. A new
pack version is a new rule-pack app version with a new tree SHA-256, delivered
before the config or bundle that pins its digest.

**Upgrade.** Superseding the base app while a required bundle app depends on it
failed in the live tenant with Intune error `0x87D300DB`; Intune did not run
Setup. This supersedence recipe is unsupported. Instead, keep the existing base
and bundle assignments, build a separate Setup-only Win32 app from the new
release (no `-ConfigPath`, no supersedence), assign it to a pilot group and
confirm its version detection. Then package and assign the next signed bundle
with the new Setup, and confirm bundle detection and enforcement. Do not remove
the old base app while bundle apps depend on it. One live test ran this
sequence: the Setup-only app installed the new release and kept the confirmed
bundle, and the next bundle built with the new Setup applied. After each Intune
upgrade, an administrator must verify an enrolled user's Claude Code hook policy
and run the documented repair with `--attest-claude-effective-policy`. Until
then, `status` can report `ok=true` with `security_complete=false` and
`security_incomplete`. Intune supersedence cannot perform the attestation;
deliver a separate elevated script or Remediation for each upgraded build.

**Change the config.** In bundle mode, deliver a new signed bundle; Setup
refuses a direct `CONFIG=` change with `bundle_required`, and refuses
`TRUSTANCHORS=` together with `CONFIG=` the same way (exit `1639`, nothing
applied). For a base-only deployment, Setup applies a new config when it runs
`/ensure` with a config that differs from the installed one. The registry rule
detects by version only, so Intune does not re-run an app for a config-only
change. To roll out a new config, re-author `config.yaml` as `config_version: 9` (see
`packaging/identity/entra/admin-config.windows.example.yaml`). The packager
refuses a missing or older version. Setup migrates an older file during install,
so its installed hash would differ from the hash pinned in the package and the
custom detection rule would never match. To change a base-only deployment:

1. Build a package from the same Setup and the new `config.yaml`.
2. Create it as a separate Win32 app, without supersedence of a base app that
   bundle apps depend on.
3. Use this custom detection script instead of the registry rule. Replace the two
   values at the top with the minimum version and the `config_sha256` value from
   the new package's `intune-package.json`:

```powershell
$minimum = [version]'X.Y.Z'
$configSha256 = 'replace-with-config_sha256-from-intune-package.json'
$base = [Microsoft.Win32.RegistryKey]::OpenBaseKey([Microsoft.Win32.RegistryHive]::LocalMachine, [Microsoft.Win32.RegistryView]::Registry64)
$key = $base.OpenSubKey('SOFTWARE\Cisco\DefenseClaw\Enterprise')
if ($null -eq $key) { exit 1 }
$version = [string]$key.GetValue('ProductVersion')
$stateRoot = [string]$key.GetValue('StateRoot')
$key.Dispose()
$base.Dispose()
$core = ($version -split '[-+]')[0]
if (-not $core -or [version]$core -lt $minimum) { exit 1 }
$config = Join-Path $stateRoot 'etc\config.yaml'
if (-not (Test-Path -LiteralPath $config -PathType Leaf)) { exit 1 }
$actual = (Get-FileHash -LiteralPath $config -Algorithm SHA256).Hash.ToLowerInvariant()
if ($actual -ne $configSha256.ToLowerInvariant()) { exit 1 }
Write-Output "DefenseClaw Enterprise $version"
exit 0
```

Devices with the old config are "not detected", so Intune runs the new package's
launcher and `ensure` re-applies the deployment with the new config. Remediations
and the installed CLI cannot apply a config change (the CLI's `ensure --config`
exits `1639`). Do not edit the installed file by hand; changes made outside Setup
are not validated.

**Roll back.** `/ensure` refuses a Setup older than the installed version
(`downgrade_refused`, `1603`), so superseding with an older app does nothing.
First remove the newer **Required** Intune assignment from the target group
(`intune_tenant.py remove-assignment --app NAME --group GROUP [--apply]`, or
remove it in the admin center). Then follow
[Roll back](/docs/enterprise/lifecycle#roll-back).

## 7. Remove DefenseClaw

First remove every **Required** assignment of the install, bundle, upgrade and
config apps from the target device group. For each app, preview and apply
`intune_tenant.py remove-assignment --app NAME --group GROUP [--apply]`, or remove
the assignment in the admin center. Then assign the base app as **Uninstall** to
that group. Intune runs `Install-DefenseClawIntune.ps1 -Uninstall`, which runs
Setup `/uninstall JSON=1`. This removes the services, hooks and machine-policy
entries, the registry marker, binaries and machine state (config, secrets, trust
anchors, bundles and receipts), and leaves enrolled accounts' per-user data and
binaries. A twin of the base app with `-Uninstall -Purge` (Setup `PURGE=1`)
removes those too. The bundle app's no-op uninstall does not remove a bundle; the
launcher refuses `-Uninstall` in a bundle package with `1639`.
`packaging/mdm/windows/uninstall.ps1 [-Purge]` does the same from any PowerShell.
Both are idempotent.

## 8. Troubleshoot

| Where | What |
| --- | --- |
| `C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\AppWorkload.log` | Intune's view of the Win32 app: download, install command, exit code, detection |
| `C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\HealthScripts.log` | Remediations runs |
| `%WINDIR%\Logs\DefenseClaw\enterprise-lifecycle.log` | Every lifecycle result, one JSON line per run |
| `%WINDIR%\Logs\DefenseClaw\mdm-wrapper.log` | The generic wrapper's steps, when you use it |
| `DefenseClaw` event log, source "DefenseClaw Lifecycle" | Installed, upgraded, repaired, failed, busy and refused events |

To see the current state on a device, from an elevated PowerShell:

```powershell
& 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe' enterprise windows status --profile standalone --json
```

| Symptom | Likely cause |
| --- | --- |
| Install fails with `1639` | No config in the package, or its `enterprise.profile` is not `standalone`. |
| Install fails with `1639` and `invalid_arguments` | The config does not parse, is not UTF-8, does not validate, or sits where a standard user can change it. `errors[].message` names the line or the folder and the fix. |
| Install fails with `1639`: the gateway service cannot read the guardrail rule pack | The rule pack is missing, or `NT SERVICE\DefenseClawGateway` cannot read it or the folder above it. Deliver it with the [rule-pack app](#custom-rule-pack-app) as a dependency, or set the permissions with the `Set-Acl` lines there, then retry. |
| Bundle app reports `1618` with `bundle_apply_failed` | The bundle verified but did not finish applying; it is not confirmed, and the base config (or the last good bundle) keeps enforcing. The error before `bundle_apply_failed` names the cause, for example `bundle_hot_apply_unavailable`, `lifecycle_busy` or `bundle_policy_not_adopted`. Intune retries `1618` three times, five minutes apart. A cause a retry cannot get past (`fleet_setup_required`, `bundle_config_validation_failed` or `bundle_install_options_changed`) reports `1603`: fix it first. `sessions_scan_unknown` alone is a warning: the running-session scan took longer than 3 seconds. |
| Failed bundle app stays NotDetected | IME may keep its GRS retry record. After preserving `AppWorkload.log`, have an Intune administrator identify the failed app ID, back up and remove only that app's stale GRS registry value under `HKLM\SOFTWARE\Microsoft\IntuneManagementExtension\Win32Apps\<identity>\GRS\...`, restart the Intune Management Extension service, then sync the device. |
| A gateway scan refuses a project inside a user profile | Run the scan as the signed-in user or move the project outside the profile. Scanner children inherit the gateway's write-restricted LocalSystem token. |
| Setup reports `user_runtime_folder_untrusted` | The upgrade went on; only that account's old hook runtime copies stay, inert, in a folder whose permissions DefenseClaw could not verify. Inspect the folder named in the warning, reset its permissions or remove it if the account no longer uses DefenseClaw, then run Setup `/ensure` again. With a pending transaction the run fails with `1603` and names the same remedy. |
| Install fails with `1603`: a named service fails during start or stop | Inspect the Windows service events and that service's log, then run Setup `/ensure` again. A standalone start has a 30-second SCM request budget and a 60-second running-state budget; each stop wait has 30 seconds. |
| Install fails with `1603` and `powershell7_required` | The PowerShell 7 dependency did not install, or is a preview build. |
| Install fails with `1603` and `mdm_hash_mismatch` | The package content changed after the packager pinned it. Rebuild it. |
| Intune reports `1618` and retries | Another lifecycle run held the lock, or a bundle did not finish applying. Intune retries three times, five minutes apart. |
| Uninstall reports `1618` with `uninstall_in_use` | A program kept running from `C:\Program Files\Cisco\DefenseClaw\bin`, or (for the `-Purge` app) kept a file in `C:\ProgramData\Cisco\DefenseClaw` open, through every Setup run. Nothing was changed, unless the message says only the data folder is left: then DefenseClaw is removed and the next run deletes that folder. The message names each program, its process id, account and parent, and the file it has open. Intune retries; if the program stays, close it or sign the account out. |
| The app installs again every day | The detection rule does not match what Setup installed: check the key path, the 64-bit setting and the version. |
| Graph still shows Installed after uninstall | The app install report lagged device detection by more than 15 minutes in the live test. Check local Intune detection or `enterprise windows status`. |
| Receipt shows `digest_unverifiable` | The bundle was signed by another product version than the device runs. The built-in policy differs by version, so the device cannot compare the signed Windows digest with its own; `files[]` hashes and the gateway's enforcing digest are still checked. Do not count it as a digest pass: re-sign the bundle with the release the devices run and deliver it again. |
| Bundle refused with `digest_mismatch` | The device runs the signer's product version and computes another Windows digest than the signed one, whatever OS signed it. A device registered under another ProgramData root computes the digest for the standard `C:\ProgramData` layout, so it refuses the same bundles. The previous bundle keeps enforcing. The message names a differing component: `builtin` means the signer build is not the devices' build, so sign with the release the devices run; any other component means the device loads that part of the policy differently, so run `bundle verify --platform windows` with the devices' release, fix the policy and sign a new version. With no component named, sign the bundle again with the release the devices run. |
| Rollback provenance | A confirmed rollback bundle records its signed `rollback_of` bundle ID in `enterprise bundle status --json` (`last_receipt`) and `bundles/receipt.json`. Text status prints `Rollback of:`. |
| Bundle changes `gateway.device_key_file` | The installed device keeps its identity at the original path. Sign a new bundle that retains the path, or reinstall the device with the new identity path. |
