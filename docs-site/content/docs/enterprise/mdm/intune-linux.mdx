Intune manages Ubuntu and Red Hat Enterprise Linux devices enrolled with the
Microsoft Intune app. It deploys Bash **platform scripts** but no Linux app
packages, so one root platform script downloads, verifies, installs and configures
DefenseClaw. You upload your copy of `packaging/mdm/linux/defenseclaw-enterprise.sh`
with its settings block and config filled in. Every day it downloads the `.deb`
(Ubuntu), the `.rpm` (RHEL) or the payload archive from your HTTPS host, installs
it when the version differs, and runs `ensure`. Health is the script's run status
plus a second root platform script with `detect.sh` and `DC_REQUIRE_HEALTHY=1`.
Removal is a root platform script with `packaging/mdm/linux/uninstall.sh`.

This recipe follows the [MDM contract](/docs/enterprise/mdm); read it first for
exit codes, detection and logs.

After the first install or a reinstall, ask users to restart agent sessions that
were already open. Those sessions keep running without DefenseClaw until
restarted. `status` and `ensure` report `agent_sessions_restart_required` while
they remain open.

## Before you start

- **Tenant**: licences and device groups are in place; see
  [Prepare your Intune tenant](/docs/enterprise/mdm/intune-tenant). Intune has no
  Linux enrollment setting.
- **Devices**: a distribution and version on Microsoft's list of Intune-supported
  Linux platforms, enrolled with the Microsoft Intune app, running systemd 239 or
  later. Where systemd is not running, the package installs but the deployment
  stays inactive. A base config delivered with a signed bundle also needs `tar`.
- **Release**: verify `checksums.txt` and read the pin of the artifact you deploy,
  as in [What you deliver](/docs/enterprise/mdm#what-you-deliver). Ubuntu needs the
  `.deb`, RHEL the `.rpm`. The payload archive works on both; the wrapper runs its
  gateway from `/var/lib/defenseclaw-mdm`, so that folder must allow execution
  (`--staging-dir` picks another root-only folder). Prefer the package on
  CIS-hardened hosts.
- **Config**: write the config as in
  [Configuration](/docs/enterprise/settings). Keep the AI
  Defense key out of it.

## 1. Host the artifact

Put the package or payload archive on an HTTPS location the devices can reach, for
example an Azure Blob Storage container or your artifact server. The wrapper
downloads with `curl` (or `wget`) and accepts only `https://` URLs. The URL must
serve the file itself: the wrapper does not follow redirects, so a GitHub release
download link fails. If the download needs a proxy, set `DC_HTTPS_PROXY` in the
next step; only the download uses it.

## 2. Fill in the wrapper's settings block

Copy `packaging/mdm/linux/defenseclaw-enterprise.sh` and edit the settings block at
the top of your copy. Intune runs the script with no arguments, so every value
goes here:

```sh
DC_ACTION=ensure
DC_SOURCE_URL="https://downloads.example.com/defenseclaw/defenseclaw-enterprise-<version>-linux-amd64.deb"
DC_SOURCE_SHA256="replace-with-the-64-hex-sha256-from-checksums.txt"
DC_TRUST_MODE=hash_pinned
DC_PRODUCT_VERSION="X.Y.Z"
```

For GPG trust, when the release ships signatures, set `DC_TRUST_MODE=signed`,
`DC_GPG_KEYRING` to a root-owned keyring you deploy separately (convert
`defenseclaw-enterprise-release-key.asc` with `gpg --dearmor`), and
`DC_SIGNATURE_URL` to the artifact's `.asc`. The wrapper still checks
`DC_SOURCE_SHA256` when you set it. Ubuntu and RHEL need different packages: create
one script per distribution and assign each to a device group that holds only that
distribution, or use the payload archive in a single script.

Then paste the config between the `DEFENSECLAW_CONFIG` markers in
`dc_inline_config`. This minimal config protects Claude Code and Codex in observe
mode; build yours from
[Choose the agents to protect](/docs/enterprise/configuration#choose-the-agents-to-protect):

```sh
dc_inline_config() {
    cat <<'DEFENSECLAW_CONFIG'
config_version: 9
deployment_mode: managed_enterprise
data_dir: /var/lib/defenseclaw
policy_dir: /etc/defenseclaw/policies
enterprise:
  profile: standalone
gateway:
  api_bind: 127.0.0.1
  api_port: 18970
guardrail:
  enabled: true
  mode: observe
  connectors:
    claudecode: {}
    codex: {}
ai_discovery:
  enabled: true
DEFENSECLAW_CONFIG
}
```

On Linux, `data_dir` must be exactly `/var/lib/defenseclaw`. Never put the AI
Defense key in the script: Microsoft states that custom scripts must not carry
sensitive information. To deliver a signed policy bundle, paste the base64 bundle
into `dc_inline_bundle` (or set `DC_BUNDLE_FILE`) and the trust anchor file into
`dc_inline_trust_anchors` (or set `DC_TRUST_ANCHOR_FILE`); the bundle carries its
own config. See
[Install order with a signed bundle](#install-order-with-a-signed-bundle).

### Install order with a signed bundle

Put the package source and the bundle in the **same** script. In that run the
package's post-install step applies the built-in default, which protects no
agents and installs no hooks. The wrapper then installs the trust anchors and
applies the bundle, so the first policy the hooks answer under is the bundle's.

A bundle-only script leaves the device unprotected if the first bundle does not
apply (an expired trust anchor, for example). To protect agents in that case,
also fill in `dc_inline_config` (or `DC_CONFIG_FILE`) with a **base config**
that matches the bundle:

- Its `guardrail:` block must match the bundle's `config.yaml` line for line,
  apart from `custom_packs.<pack>.path`. The bundle names `policies/guardrail/<pack>`
  inside itself; the base config names the absolute folder where a separate root
  script installed the same pack before this one runs. Only root may change that folder.
  On Linux it must be outside `/etc/defenseclaw`, which an uninstall with purge
  removes.
- Its `claude_code:`, `codex:`, `connector_hooks:` and `application_protection:`
  blocks must match the bundle's, or be left out of both. A `mode` in
  `claude_code`, `codex` or `connector_hooks.<connector>` overrides the guardrail
  mode for that agent, so a base config that sets `mode: observe` there only
  reports calls the bundle blocks. Comments and blank lines don't count.
- No other setting is compared. Copy every other enforcement setting the bundle
  sets, such as `asset_policy:`, into the base config too, or the base config can
  allow what the bundle blocks until the bundle applies.
- The wrapper compares these blocks as text, so write the base config plainly:
  ASCII only, with LF or CRLF line endings (a tab, a lone CR or a non-ASCII byte
  is refused, even in a comment; one UTF-8 byte order mark at the start is
  allowed). Write each top-level key in lowercase, plain or in quotes without
  escapes, and end every quoted value and every `{...}` or `[...]` on the line
  where it starts. A tag, anchor, alias, merge key, `?` key, or a document written
  as one `{...}` is refused.
- Before it installs anything, the wrapper refuses a different threshold, mode,
  connector list or digest, a missing rule pack, a relative pack path, or a
  different hook-mode block with `mdm_base_config_mismatch` (exit `2`). The
  comparison reads the bundle with `tar`; without `tar` the wrapper installs
  nothing and exits `1` with `mdm_tar_missing`. Minimal RHEL 9 and Rocky Linux 9
  images lack it (`dnf install tar`).
- On a device not yet in bundle mode, the wrapper applies the base config first,
  then the trust anchors, then the bundle. With a matching base config the bundle
  usually applies in the running gateway without a restart. Once the anchors are
  installed, only bundles apply and the base config is no longer used.

Do not deploy a base config in an earlier, separate script whose guardrail
block differs from the bundle's. Until the bundle applies, agents run under that
base config, so it can allow calls the bundle denies.

## 3. Add the platform script

In the Intune admin center, go to **Devices** > **Manage devices** >
**Configuration** > **Create** > **New policy** > **Linux** > **Settings catalog** >
**Create profile** > **Custom Configuration (linuxMdm)**. Complete **Basics**,
**Configuration settings**, **Scope tags**, **Assignments**, then
**Review + create**. The review page may show **Platform: No Platform** for this
Linux profile.

| Setting | Value |
| --- | --- |
| Execution context | **Root**. The Intune daemon still needs authorization for `com.microsoft.intune.actions.ConfigureDevice`; see the polkit rule below. |
| Execution frequency | **Every 1 day**. `ensure` changes nothing when the host already matches, but with `DC_SOURCE_URL` set every run downloads the artifact before it compares versions. |
| Execution retries | **No retries**. The wrapper itself retries exit `75` (busy) up to three times, 10 seconds apart. Intune may count a cached retry inside its frequency window as successful without rerunning the script. |
| Execution script | Your edited copy of `defenseclaw-enterprise.sh` (upload it, or paste it in **Bash Script**) |

Assign it to device groups. On each run the wrapper downloads the artifact,
verifies it, installs the package only when its version differs, runs `ensure` with
the config, and exits with the lifecycle's code. A busy package manager, for
example during unattended upgrades, exits `75` (`mdm_package_manager_busy`). Intune
checks in about hourly; a failed non-busy run waits for a later frequency window.
An older `.deb` is refused before `dpkg -i` changes the host.

For a local-group profile assignment, upload
`packaging/mdm/intune/linux/sync-local-group.sh` as a **second** root platform
script. Edit `GROUP_NAME` and the complete `MEMBERS` array first; the script creates
the local group if needed and updates its supplementary members only when they
differ. It refuses pre-existing groups unless a root administrator has reviewed and
claimed them by writing their numeric GID to
`/var/lib/defenseclaw-intune/local-groups/<group-name>` (root-only directory and
file). Use a dedicated group: claiming a system or privileged group would let the
script replace its entire supplementary member list. A Linux Intune enrollment does
not import Entra group membership into the OS, so maintain this list from your
identity source. Changing it affects `profile-explain` after the host's directory
cache refresh; live hooks may keep the previous profile for up to 15 minutes.

For unattended root scripts, authorize only your enrolled Intune users for the
daemon's polkit action. Without this, an xrdp or SSH session has no active local
seat and the daemon can fail before the script starts. Put enrolled users in a
dedicated local group and install this root-owned file as
`/etc/polkit-1/rules.d/49-intune-scripts.rules`:

```javascript
polkit.addRule(function(action, subject) {
    if (action.id === "com.microsoft.intune.actions.ConfigureDevice" &&
        subject.isInGroup("intune-script-operators")) {
        return polkit.Result.YES;
    }
});
```

Restrict that group to users allowed to trigger device configuration. A console
administrator can instead authenticate at the polkit prompt. A policy edit reaches
a device at its next agent check-in (about one hour plus up to ten minutes), or
after the user selects **Refresh** in the Intune app; the test device applied
changes one to six minutes after Refresh, with one rapid second edit taking over
15 minutes.

## 4. Report health

The platform script's own run status is the first signal: it fails whenever
`ensure` fails. For a separate health signal, add a second root platform script: a
copy of `packaging/mdm/linux/detect.sh` with `DC_REQUIRE_HEALTHY=1` and, optionally,
`DC_MIN_VERSION="X.Y.Z"` in its settings block. In the default `exit` format it
exits `0` when DefenseClaw is installed, new enough and passes `verify`, and `1`
otherwise. Set its retries to **No retries**.

Intune's custom compliance cannot run `detect.sh`: Microsoft runs Linux discovery
scripts in the signed-in user's context, and DefenseClaw's status is readable only
by root. A failed platform script also does not make a Linux device noncompliant.
In the test tenant, the install script and a bundle-aware `detect.sh` both exited
`1` after the device refused a bundle with a bad signature (`signature_invalid`),
yet Graph and the admin center showed the device as **Compliant**. So do not use
the compliance state, or a Conditional Access rule built on it, to tell whether the
signed bundle applied. Read each script's per-device status instead (open the
script's configuration profile and select **Device status**, or collect the
results through Graph). On the device,
`sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise bundle status --json`
names the refused bundle and its error code under `last_refusal`. The package
database answers inventory for the deb and rpm channels:

```bash
dpkg-query -W -f='${Status} ${Version}\n' defenseclaw-enterprise
rpm -q defenseclaw-enterprise
```

## Deliver the Cisco AI Defense key

After DefenseClaw is installed, deliver the key once through an administrator
channel, such as SSH, your configuration-management tool or a secrets agent that
runs as root. First make sure the config turns the feature on; see
[Cisco AI Defense key](/docs/enterprise/ai-defense-key).

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret set \
  --name ai-defense-api-key --from-file /root/ai-defense.key
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise secret status
```

Or, from tooling that can drop a root-only file, run the wrapper with
`--secret-name ai-defense-api-key --secret-file /path/to/root-only-file`. Delete the
source file afterwards. Storing the key re-runs `ensure`, which applies it.

## Change the config, upgrade and roll back

- **Change the config**: edit the config in the script and save it. The next run
  validates and applies it. An invalid config fails the run with `config_invalid`
  and leaves the installed config unchanged.
- **Upgrade**: host the new artifact, then update `DC_SOURCE_URL`,
  `DC_SOURCE_SHA256` and `DC_PRODUCT_VERSION`. Keep each host on one channel: a host
  installed from the deb or rpm refuses a payload-archive upgrade.
- **Roll back**: `rpm -U` refuses an older rpm. See
  [Roll back](/docs/enterprise/lifecycle#roll-back).

## Remove DefenseClaw

If the config names a custom rule pack, run and confirm the pack-delivery script
before the package and config script. After an uninstall with purge,
`/etc/defenseclaw` and its pack are gone. Reassign or change the pack script so
Intune executes it again, confirm the pack is staged, then reassign the install
script. A missing pack causes `config_invalid`; do not retry the install before the
pack is restored.

First remove the devices from the install script's assignment. Then assign a root
platform script with `packaging/mdm/linux/uninstall.sh`; set `DC_PURGE=1` in its
settings block for a purge. What it removes is in
[Uninstall](/docs/enterprise/mdm#uninstall). On a host with nothing installed it
exits `0`, so repeated runs are harmless. A plain removal keeps your policies in
`/etc/defenseclaw/policies`; `DC_PURGE=1` removes them. To keep the machine state for a
reinstall, see [Uninstall](/docs/enterprise/lifecycle#uninstall).

## Notes

- **SELinux**: after installing files, the lifecycle runs `restorecon` on
  `/opt/defenseclaw` and `/etc/defenseclaw`.
- **Logs**: the wrapper writes `/var/log/defenseclaw-enterprise-mdm.log` (root,
  `0600`). The package's own `ensure` result is in
  `/var/lib/defenseclaw-enterprise/last-package-result.json`.
- **Status on a device**:

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux status --json
```
