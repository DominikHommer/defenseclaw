Deploy the standalone profile in six steps. Each step makes one decision and
links to the page with the details. You need an MDM, configuration-management
tool or administrator shell that runs commands as SYSTEM on Windows and as root
on Linux and macOS. [Concepts](/docs/enterprise/concepts) defines *profile*,
*lifecycle* and *ensure*. Not sure you need enterprise deployment? Read
[Is this for you?](/docs/enterprise#is-this-for-you).

## 1. Pick the profile

A managed deployment runs in one of two profiles, and each computer runs only
one of them.

| Detail | Standalone | Secure Client |
| --- | --- | --- |
| Choose it when | You deploy with Intune or any other MDM, a package, configuration management or an administrator shell | You run Cisco Secure Client and want DefenseClaw as one of its modules |
| Platforms | Windows, Linux, macOS | Windows, macOS |
| Who decides on each tool call | The local policy engine. Cisco AI Defense is added when you turn it on and store a key | Cisco AI Defense only |
| Next | Continue with step 2 on this page | [Secure Client managed deployment](/docs/enterprise/secure-client) |

The rest of this page covers the standalone profile. On Windows and macOS the
profile defaults to Secure Client, so set `enterprise.profile: standalone`
([Two profiles](/docs/enterprise#two-profiles)).

## 2. Pick the agents

Each agent you protect is a key under `guardrail.connectors` in the config.
Nothing is protected until you list one. DefenseClaw protects each agent in
one of two ways:

| Route | Agents | What DefenseClaw writes |
| --- | --- | --- |
| [Machine policy](/docs/enterprise/concepts#machine-policy-connector) | Claude Code, Codex, Cursor, GitHub Copilot, and OpenCode with DefenseClaw's managed OpenCode plugin | Its hooks in the vendor's administrator-owned policy files, which apply to every user of the computer |
| [Per-user](/docs/enterprise/concepts#per-user-connector) | Devin, Antigravity, Hermes, Amp and Kiro, and OpenCode while the managed plugin is not in force | The guardian writes the hook, or plugin, into each enrolled user's own agent config and repairs it |

OpenClaw and ZeptoClaw are not supported in enterprise managed mode.

ACP (Agent Client Protocol) editors are a separate route, in preview, and not a
`guardrail.connectors` key. The central config needs `acp.enabled: true`, a
binding for each editor and agent pair, and an ACP profile that allows both
([ACP configuration](/docs/reference/acp-guard#configuration)). Then enroll each
user with `defenseclaw-gateway enterprise acp enroll --user --client --agent
--profile` ([Managed computers](/docs/reference/acp-guard#managed-computers)).
Enrollment refuses a pair the config does not allow.

The verified agent and OS combinations are in the
[enterprise route table](/docs/support-matrix#enterprise). How to list agents,
users and per-agent modes is in
[Choose the agents to protect](/docs/enterprise/configuration#choose-the-agents-to-protect)
and [Plan a rollout](/docs/enterprise/rollout#step-1-choose-the-agents).

the scripts in
[`packaging/mdm`](https://github.com/cisco-ai-defense/defenseclaw/tree/main/packaging/mdm).
Each card names what you push.

The release files the recipes deliver:

| OS | Release file |
| --- | --- |
| Windows x64 | `DefenseClawSetup-Enterprise-Standalone-x64.exe` |
| Linux | `defenseclaw-enterprise-<version>-linux-<arch>.deb` or `.rpm`, or the payload archive `defenseclaw-enterprise-<version>-linux-<arch>.tar.gz` |
| macOS (Apple silicon) | `defenseclaw-enterprise-<version>-darwin-arm64.pkg` |

`<arch>` is `amd64` or `arm64`. `DefenseClawSetup-Enterprise-x64.exe`, without
`-Standalone-`, is the Secure Client Setup. Verify the release's signed
`checksums.txt` once and pin each file by its SHA-256, as
[What you deliver](/docs/enterprise/mdm#what-you-deliver) shows.

## 4. Deliver the config and the AI Defense key

The config is one YAML file that only administrators can change. It is the only
policy the host enforces: thresholds, block and allow lists, rule packs and the
agents to protect all live in it, and local tools cannot change it
([Policy changes on a managed host](/docs/enterprise#policy-changes-on-a-managed-host)).
The lifecycle installs it at a fixed path:

| OS | Installed config |
| --- | --- |
| Windows | `C:\ProgramData\Cisco\DefenseClaw\etc\config.yaml` |
| Linux | `/etc/defenseclaw/config.yaml` |
| macOS | `/opt/cisco/defenseclaw/etc/config.yaml` |

Start from [A minimal config](/docs/enterprise#a-minimal-config), which
protects Codex and Claude Code in observe mode. A first install on Windows
needs a config. On Linux and macOS an install without one protects no agents.
How each wrapper takes the config is in
[Deliver the config](/docs/enterprise/mdm#deliver-the-config).

The Cisco AI Defense key is optional. It never goes in the config, an MDM
script or a command line. Store it with `enterprise secret set`, from
standard input or a file only administrators can change: after the install
on Windows, and before or after it on Linux and macOS; see
[Deliver the AI Defense key](/docs/enterprise/mdm#deliver-the-ai-defense-key)
and [Cisco AI Defense key](/docs/enterprise/ai-defense-key).

## 5. Run ensure and read the result

`ensure` is the one action your MDM runs. It installs when nothing is
installed, upgrades when the version differs, repairs drift and applies a
changed config. When the host already matches, it changes nothing and reports
`"noop": true`, so it is safe on every check-in. The kit's wrappers print one
result document per run and exit with one of these codes:

| Result | Windows | Linux, macOS | MDM action |
| --- | --- | --- | --- |
| Success, or nothing to do | `0` | `0` | Success |
| Failed. The change has already rolled back | `1603` | `1` | Read `errors[].code` |
| Another run or the package manager is busy | `1618` | `75` | Retry later |
| Invalid arguments, such as a first Windows install without a config | `1639` | `2` | Fix the assignment |

For MDM detection, use the registry marker (Windows), the package database or
pkg receipt for inventory, and `detect.ps1` or `detect.sh` with the health
option for health; see [Detection](/docs/enterprise/mdm#detection). To check a
host by hand:

<Tabs items={['Linux', 'macOS', 'Windows']}>
  <Tab value="Linux">

```bash
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux status --json
sudo /opt/defenseclaw/bin/defenseclaw-gateway enterprise linux verify --json
```

  </Tab>
  <Tab value="macOS">

```bash
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos status --json
sudo /opt/cisco/defenseclaw/bin/defenseclaw-gateway enterprise macos verify --json
```

  </Tab>
  <Tab value="Windows">

```powershell
# From an elevated PowerShell
$Cli = 'C:\Program Files\Cisco\DefenseClaw\bin\defenseclaw.exe'
& $Cli enterprise windows status --profile standalone --json
& $Cli enterprise windows verify --profile standalone --json
```

  </Tab>
</Tabs>

Read `coverage_complete` and `security_complete` in the result
([Health fields](/docs/enterprise/operations#health-fields)). On Linux and
macOS, `policy.effective_digest` and `policy.applied` say which config the host
runs and whether the gateway applied it
([Effective policy digest](/docs/enterprise/operations#effective-policy-digest-and-config-generation)).
Every exit code is listed in [Exit codes](/docs/enterprise/mdm#exit-codes).

## 6. Pilot in observe mode, then expand in rings

Deploy a pilot ring with `guardrail.mode: observe`. Observe mode records every
decision, including what DefenseClaw would have blocked, without blocking on
policy verdicts. When the pilot is healthy and you have reviewed the decisions,
set `guardrail.mode: action` and deliver the config again. Then grow in rings
(pilot, early, broad, everyone), moving on only when a ring is healthy.
[Plan a rollout](/docs/enterprise/rollout#step-5-expand-in-rings) has ring
sizes and exit criteria.
