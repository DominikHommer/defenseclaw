The audit DB is connector-agnostic. Current canonical events persist a
`connector` column, so adding or replacing connector wiring does not erase
history. New events land under the connector that produced them; migrated
legacy or unclassified rows may have an empty connector value.

## Try it

<Steps>

<Step>

### Inspect current state

```bash
defenseclaw status
defenseclaw alerts --limit 25
defenseclaw-gateway audit export --limit 500 --newest \
  | jq -r 'select(.connector) | .connector' | sort | uniq -c
```

`status` shows enforcement flags plus a per-connector block for every active
connector. `alerts` lists the most recent decisions as a table. The last
command counts the 500 newest audit rows by connector.

</Step>

<Step>

### Add or reconfigure the connector

```bash
defenseclaw setup codex
```

Setup asks these questions in this order. The first one is the enforcement mode,
answered with a number:

```text
  Enforcement mode for Codex
  ──────────────────────────
    [1] observe — scan and report findings, never block (recommended to start)
    [2] action  — scan and block/confirm when policy requires (PreToolUse deny)
  Select mode (1, 2) [1]:
```

Type `1` (observe) or `2` (action), or press Enter for the default. Letters are
rejected here. Passing `--mode observe` or `--mode action` answers this question,
so setup does not ask it.

If another connector is already wired (here, `claudecode`), setup prints what it
will change and then asks how to combine them:

```text
  DefenseClaw is already configured for: claudecode
  You are setting up: codex
    [a] Add     — run it alongside the existing connector(s) (multi-connector)
    [r] Replace — switch to only this connector
    [c] Cancel  — make no changes
  Choose (a, r, c) [a]:
```

Type `a` to keep both active. Type `r` only when you want DefenseClaw to tear
down the previous connector's agent-side files before wiring the new one. `c`
makes no changes.

If you chose action mode, setup then offers the LLM judge:

```text
  Add LLM judge on top of rule scanning? [y/N]:
```

Press Enter or type `n` to keep rule scanning only, or `y` to add the judge
(configure its model with `defenseclaw setup llm`). Observe mode skips this
question. `--enable-judge` or `--no-enable-judge` answers it.

To replace instead of add, pass `--replace`. Setup then asks a yes/no question
in place of the Add/Replace/Cancel choice, followed by the judge question in
action mode:

```bash
defenseclaw setup claude-code --replace --mode action
```

```text
  Replace codex with claudecode? This removes the other connector(s). [y/N]: y
  Add LLM judge on top of rule scanning? [y/N]: n
```

For an unattended run, `--yes` asks nothing and takes the add/reconfigure path.
Use `--replace` only when replacement is intentional:

```bash
defenseclaw setup codex --yes
defenseclaw setup codex --yes --replace
```

Use `--mode action` when this connector should block policy hits immediately:

```bash
defenseclaw setup codex --mode action
```

</Step>

<Step>

### Verify

```bash
defenseclaw doctor
defenseclaw alerts --limit 10
defenseclaw-gateway audit export --connector codex --since 30m
```

`doctor` confirms connector health. `alerts` and the audit export, filtered to
`codex` and the last 30 minutes, show new events landing under `codex`.

</Step>

</Steps>

## What stays, what changes

| Stays put | Changes |
| --- | --- |
| Audit DB (`~/.defenseclaw/audit.db`) | Active connector roster |
| Rule packs (`~/.defenseclaw/policies/`) | Hook scripts wired in agent config |
| Admission and the block/allow lists (`admission` and `asset_policy` in `config.yaml`) | Rules that name the removed connector (`connector: codex`), which no longer match anything |
| Observability destinations and notifier webhooks | `guardrail.connectors.<name>` policy blocks |
| Historical audit attribution | Backed-up agent files for removed or replaced connectors |

<Callout type="info">
Use **Add** for multi-connector hosts. Use **Replace** only for a deliberate
one-connector workstation. To retire a connector later, run
`defenseclaw setup remove <connector>`. Removing the last configured connector
requires `--force`.
</Callout>

## When to change connector wiring

- Trying a different agent. Add the second connector and compare behavior from `defenseclaw status` and `defenseclaw alerts`.
- Promoting an agent. Re-run `defenseclaw setup <connector> --mode action` when a connector should start blocking.
- Demoting an agent. Re-run `defenseclaw setup <connector> --mode observe` while you tune policy.
- Retiring an agent. Run `defenseclaw setup remove <connector>` after you stop
  using it; add `--force` only when removing the last connector is deliberate.

## Caveats

<Callout>
The audit DB is portable across connectors but not across DefenseClaw versions in some cases. Use [`defenseclaw upgrade`](/docs/get-started/upgrade), which runs `defenseclaw migrate` before restarting the gateway; `defenseclaw migrate --check` reports anything still pending.
</Callout>
