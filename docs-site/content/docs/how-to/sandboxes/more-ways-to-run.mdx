Run flags and settings for the cases the default run does not cover. Each section is one recipe. [Run an agent](/docs/how-to/sandboxes/run-an-agent) covers the default run, and the [sandbox CLI reference](/docs/reference/sandbox-cli#sandbox-run) lists every flag.

## Before you start

- Sandboxes are set up and `defenseclaw sandbox doctor` ends with `ready for sandboxes`.
- You are in the project folder.

## Work on a copy

For an untrusted repository or task:

```bash
defenseclaw sandbox run codex --copy
```

DefenseClaw copies the folder into the sandbox (a shallow git clone plus your working tree, with secret files held back). Nothing reaches your folder until you [pull](/docs/how-to/sandboxes/review-undo-or-pull#pull-on-macos). What git ignores (`node_modules/`, `.venv/`, build output) and package caches are not copied, so install dependencies inside. Every run on a Mac works on a copy. When a folder's git state cannot be protected in place (a linked worktree, `.git` as a symbolic link, a git directory outside the folder), `run` says why and starts in copy mode.

## Run agents in parallel

Only one sandbox at a time can mount a folder live. Give each parallel run its own name and copy:

```bash
defenseclaw sandbox run claude --copy --name fix-tests
defenseclaw sandbox run codex --copy --name docs
```

Each one's work can come back as its own branch (`dc/fix-tests`, `dc/docs`). Names use at most 19 lowercase letters, digits and `-`. A second live run on a folder a sandbox already mounts is refused with a hint to use `--copy` or delete the other sandbox. If a sandbox already holds this folder for the same harness, an interactive `run` without `--name` asks whether to resume it, and `--new` starts another.

## Run in the background

A detached run needs a prompt:

```bash
defenseclaw sandbox run claude --detach --prompt "fix the failing tests"
```

```text
  ✓ Claude Code is running in the background in myapp-7f3a
  follow:  defenseclaw sandbox logs myapp-7f3a -f
  watch:   defenseclaw sandbox activity -f --sandbox myapp-7f3a
  review:  defenseclaw sandbox review myapp-7f3a   undo: defenseclaw sandbox undo myapp-7f3a
  stop:    defenseclaw sandbox stop myapp-7f3a
```

`sandbox logs NAME` shows the run's output (`-f` follows it, `-n` sets the lines) and says whether it is still going, finished with its exit status, or was interrupted. A stop keeps the last 1 MiB of the log. A detached run has no end-of-session prompt: use `review` and `undo`, or `pull` on a copy. `--detach` cannot be combined with `--rm`.

## Add a reference folder

```bash
defenseclaw sandbox run claude --context ~/code/shared-lib
```

The folder is mounted read-only beside the project at `/work/shared-lib`, with its secret files hidden. Repeat `--context` for more. They cannot overlap the project or each other. A copy-mode run and every MicroVM run refuse `--context`: put a copy of the folder inside the project.

## Give the agent a project secret

```bash
defenseclaw sandbox run claude --credential STRIPE_API_KEY=api.stripe.com
```

The sandbox gets a placeholder in `$STRIPE_API_KEY` that works only against `api.stripe.com` (add `:port` for another port). OpenShell swaps in the real value from your shell, in headers and query strings of requests to that host. The value never enters the sandbox, and a host on a blocklist cannot be bound.

## Give the agent your GitHub token

```bash
defenseclaw sandbox run claude --github-write
```

The sandbox gets placeholders in `GH_TOKEN` and `GITHUB_TOKEN`. OpenShell swaps in your token (from either variable in your shell) only on requests to `api.github.com`, which `gh` uses to open pull requests. It is not bound to `github.com`, so a `git` command that authenticates there does not get it. Without the flag, the agent has no GitHub credential.

## Choose the model credential

By default (`--llm auto`) a run shares the first model credential it finds:

| Harness | Looks for |
| --- | --- |
| Claude Code | `ANTHROPIC_API_KEY`, then `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`), then `AWS_BEARER_TOKEN_BEDROCK` |
| Codex | `OPENAI_API_KEY` or `CODEX_API_KEY`, then the API key a `codex login --with-api-key` stored in `~/.codex/auth.json` (a ChatGPT login is not shared), then `AWS_BEARER_TOKEN_BEDROCK` |
| OpenCode | `ANTHROPIC_API_KEY`, then `OPENAI_API_KEY`, then `AWS_BEARER_TOKEN_BEDROCK` |
| GitHub Copilot CLI | `ANTHROPIC_API_KEY` as Copilot's bring-your-own-provider key, then `AWS_BEARER_TOKEN_BEDROCK` |
| Hermes Agent | `OPENAI_API_KEY`, then `ANTHROPIC_API_KEY`, then `AWS_BEARER_TOKEN_BEDROCK` |
| Antigravity | `GEMINI_API_KEY`. Without it you sign in with Google inside the sandbox. |

`--llm` picks one explicitly (`anthropic`, `claude-oauth`, `openai`, `bedrock` or `gemini`), and `--llm none` shares nothing, so you log in inside the sandbox. `openshell.llm` in `config.yaml` sets the same choice for every run without `--llm`, including runs the shell wrappers, the TUI and the macOS app start:

```yaml
openshell:
  llm: bedrock    # auto (the default) | none | anthropic | claude-oauth | openai | bedrock | gemini
```

A provider the harness has no profile for gives way to `auto`, and the run says so. A provider whose key is not set refuses the run and names the key. `--llm bedrock` uses `AWS_BEARER_TOKEN_BEDROCK` and `--bedrock-region` (default `$AWS_REGION`, then `$AWS_DEFAULT_REGION`, then `us-east-1`). Codex on Bedrock runs `openai.gpt-5.5` and Hermes Agent `openai.gpt-oss-20b` unless `-- -m MODEL` picks another. A login you do inside a kept sandbox stays in it and is readable by the agent, so prefer an API key.

When the provider rejects the key, DefenseClaw says so in the feed, in `sandbox status` (a **Model key** row) and in the session summary. Put a fresh key in your shell, stop the session, and run `defenseclaw sandbox connect NAME` from that shell, which hands the sandbox the new key.

## Use a service on your machine

```bash
defenseclaw sandbox run claude --host-port 5432
```

Inside the sandbox the service is at `host.openshell.internal:5432`, and the banner's `Host` line lists the port. A connection to your machine is a door into it, so the first connection arrives as an ask for you to [approve](/docs/how-to/sandboxes/unblock-a-site#answer-an-ask). DefenseClaw's own ports and the OpenShell gateway's are never opened. A port the run did not list stays closed, and the feed names the flag to add.

On a machine several accounts use, another account's DefenseClaw ports look like ordinary ports to yours, so the ask is the only gate. Approve only a port whose service you know.

## Keep the harness prompts

```bash
defenseclaw sandbox run claude --safe
```

The harness asks before commands as it does outside a sandbox. Flags after `--` that would turn its prompts off are dropped, with a warning. Codex asks before every command outside its read-only set (`approval_policy="untrusted"`), so a headless `--safe` Codex run refuses those commands.

## Bring your MCP servers along

For Claude Code and Codex, a run brings your user-scope MCP servers (`~/.claude.json`, `~/.claude/settings.json`, `~/.codex/config.toml`). They run inside the sandbox under the same limits, and the hooks see every MCP tool call. The banner's `MCP` line lists them.

A server stays behind, with a warning, when DefenseClaw blocks it (an `asset_policy.mcp.denied` rule that `defenseclaw mcp block` writes, a scan verdict, or the MCP asset policy in `action` mode), when it is disabled or runs on this machine (a `localhost` or private URL), or when it uses a transport the harness cannot run in a sandbox (Codex has no SSE). Environment values and HTTP headers never enter the sandbox. To give a server its secret, bind it with `--credential NAME=host`. `--no-mcp` leaves all of them behind.

The repository's own servers (`.mcp.json` for Claude Code, `.codex/config.toml` for Codex) start without a tool call, so the hooks would never see them start. They stay blocked unless a custom pack sets `mcp.project_servers: allow`. For Codex, your servers whose name the repository also uses stay behind, because Codex would merge the repository's entry into yours. The other harnesses do not bring MCP servers along, and the `strict` pack leaves every server behind.

DefenseClaw writes the result into each sandbox's managed harness configuration, mounted read-only: Claude Code gets `/etc/claude-code/managed-mcp.json` (its exclusive MCP mode) plus an allowlist, and Codex gets an `mcp_servers` allowlist in `/etc/codex/requirements.toml` and the definitions in `/etc/codex/managed_config.toml`. So `claude mcp add` inside a sandbox is refused. Add the server on your machine in user scope (`claude mcp add --scope user …`) and start a new sandbox. A resumed sandbox keeps the servers it was created with.

## Make `claude` run sandboxed

```bash
defenseclaw sandbox enable claude
```

```text
  ✓ `claude` now runs in a DefenseClaw sandbox in new zsh sessions (~/.zshrc)
  apply it now: source ~/.zshrc · bypass once: DEFENSECLAW_NO_SANDBOX=1 claude · undo: defenseclaw sandbox disable claude
```

`enable` adds a marked block to your shell's rc file (`~/.bashrc`, `~/.zshrc` or fish's `config.fish`; `--shell` and `--rc` choose another) that defines a `claude` function starting `sandbox run claude`. Everything you type after `claude` passes through to the harness.

- `DEFENSECLAW_NO_SANDBOX=1 claude` runs the harness directly, once, where your organization allows it. On a managed computer whose policy lists the agent in `required_for`, the host run is refused by the agent's machine-owned hook unless your account is in `enterprise.enrollment.exempt_users`, or sandboxes are unavailable to your account and the effective `when_unavailable` is `alert` ([Require sandboxes](/docs/enterprise/sandboxes#require-sandboxes)).
- Inside a sandbox the wrapper runs the harness directly.
- If the DefenseClaw launcher is missing, the wrapper prints the fix and never runs unsandboxed.
- `defenseclaw sandbox disable claude` removes the wrapper from every rc file. Open a new shell.

In the TUI Sandboxes panel, `w` switches the `claude` and `codex` wrappers on and off. `defenseclaw sandbox doctor` reports installed wrappers. Kiro CLI gets no wrapper: start it with `defenseclaw sandbox run kiro`.

## Other flags

| Flag | Effect |
| --- | --- |
| `--unmask GLOB` | Share a hidden secret file (repeatable). A copy never takes git-ignored files, unmasked or not. |
| `--env KEY=VALUE` | A non-secret environment variable (repeatable). |
| `--no-snapshot` | Skip the pre-session snapshot and with it undo (mount mode). |
| `--rm` | Delete the sandbox when the session ends. A copy whose work was not brought back is kept. |
| `--keep` | Keep a headless run's sandbox. `openshell.keep_headless: true` keeps them all. |
| `--refresh` | When resuming a copy, copy the folder again. |
| `--cpu`, `--memory` | Resource limits, for example `--cpu 2 --memory 4Gi`. No effect on a MicroVM. |
| `--no-build` | Fail instead of building a missing image. |
| `--process-tree` | Sample the sandbox's processes for `sandbox ps --tree`. |

## Check it worked

`defenseclaw sandbox list` shows each sandbox with its harness, mode and profile, and the banner of each run shows the flags it took.

## Undo

Delete a sandbox with `defenseclaw sandbox delete NAME`. Remove a wrapper with `defenseclaw sandbox disable claude`. Unset `openshell.llm` to return to `auto`.
