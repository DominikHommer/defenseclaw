Install and configure OpenShell sandboxes on an Apple-silicon Mac. Each sandbox is a small virtual machine (a MicroVM) with its own Linux kernel, the agent works on a copy of your project, and you bring its changes back when you are happy with them.

## Before you start

| You need | Details |
| --- | --- |
| A Mac with Apple silicon | The MicroVM driver runs on Apple silicon only. On an Intel Mac sandboxes are refused. If you run the Intel build of DefenseClaw under Rosetta, install the arm64 build. |
| DefenseClaw | Installed and initialized ([quickstart](/docs/get-started/quickstart)), with the daemon running. The [macOS app](/docs/features/macos-app) starts it for you. Run everything as your own user. |
| [Homebrew](https://brew.sh) | OpenShell installs from NVIDIA's `nvidia/openshell` formula and its gateway runs as a Homebrew service. NVIDIA's installer runs Homebrew as you, without `sudo`, so your account must be able to write to Homebrew's folders ([another account's Homebrew](#a-homebrew-that-belongs-to-another-account)). |
| Xcode or the Command Line Tools | Current for your macOS release. Homebrew may build the formula from source and checks them first ([developer tools](#developer-tools)). |
| `e2fsprogs` | The MicroVM driver formats each MicroVM's disks with its `mke2fs` and `debugfs`. Setup offers to install it with Homebrew. The driver looks only in the Homebrew kegs under `/opt/homebrew` and `/usr/local`. |
| Docker Desktop, running | DefenseClaw builds the harness images in Docker, and the MicroVM driver reads them from it. Start it once on your own account first ([first start](#docker-desktops-first-start)). |
| Disk | At least 5 GiB free for Docker, 10 GiB recommended. The first image build downloads about 3 GB. A MicroVM image's first start uses about 11 GiB of free host space while it prepares its disk (the VM volume needs at least 12 GiB free, 22 GiB recommended). The driver then keeps a disk of about 5 GB per image it has started. |

On a Mac your organization manages with a standalone enterprise install, an administrator provides OpenShell and `e2fsprogs`, and the managed setup mode needs no Homebrew on your account: [Sandboxes on managed computers](/docs/enterprise/sandboxes).

### Developer tools

When NVIDIA's tap has no prebuilt package for your macOS release, Homebrew builds the formula and stops if Xcode or the Command Line Tools are too old (`Your Xcode (26.2) … is too outdated`). Update them as Homebrew says, then run setup again.

<Callout type="warn" title="Homebrew checks Xcode.app even when you use the Command Line Tools">
Homebrew looks at `/Applications/Xcode.app` even when `xcode-select` selects the Command Line Tools. If the tools are current but that Xcode is old, setup says `Homebrew checks Xcode 26.2 at /Applications/Xcode.app even so`. Update that Xcode or delete it.
</Callout>

### Docker Desktop's first start

The first time Docker Desktop starts on your account it asks you to install Rosetta (when missing), allow local-network access, accept its licence, and type an administrator's name and password for its privileged helper. On a standard account, have an administrator type the password. Setup does not answer these prompts. Its Docker check fails until Docker Desktop has started once.

### A Homebrew that belongs to another account

Setup checks `Library/Taps` and `Cellar` under the Homebrew prefix before it runs NVIDIA's installer, and stops with the owner and folder:

```text
  ✗ install OpenShell: Homebrew at /opt/homebrew belongs to admin, and you (alice) cannot write to /opt/homebrew/Library/Taps, where Homebrew adds NVIDIA's tap and installs the formula
  → ask admin (or an administrator) to make /opt/homebrew writable for you, or use a Homebrew of your own (…)
```

Either have the owner give you write access, or install a Homebrew of your own in your home directory, put it first on `PATH` with `eval "$(~/homebrew/bin/brew shellenv)"`, and run setup again. A Homebrew of your own works with three differences. The install plan passes `OPENSHELL_LOCAL_TLS_DIR=<prefix>/var/openshell/tls` to NVIDIA's installer. Homebrew has no prebuilt packages for such a prefix, so it may build for many minutes. And the driver never finds an `e2fsprogs` installed there, so setup stops and asks an administrator to run `brew install e2fsprogs` with a Homebrew under `/opt/homebrew` or `/usr/local`. When the OpenShell CLI is outside `/usr/bin`, `/usr/local/bin` and `/opt/homebrew/bin`, setup records its path as `openshell.binary` in `~/.defenseclaw/config.yaml`.

### Run setup

<Tabs items={['Command line', 'TUI', 'macOS app']}>
<Tab value="Command line">

```bash
defenseclaw sandbox setup
```

```text
DefenseClaw sandbox setup
  Checking this machine…  ✓ darwin/arm64  ✓ Landlock (MicroVM)  ✓ Docker 29.1.5  ✗ OpenShell and its MicroVM driver not installed
Install OpenShell … with NVIDIA's installer? (Homebrew; sha256 verified) [y/N] y
```

Setup then:

1. Installs OpenShell from the `nvidia/openshell` formula, without `sudo`. The plan lists what else changes: Homebrew may update itself first, and the gateway is registered as `openshell` in `~/.config/openshell`. With the same consent it installs `e2fsprogs` when missing.
2. Switches the gateway to MicroVMs. Docker Desktop's Linux kernel has no Landlock, so the Docker driver cannot run sandboxes there.

   ```text
   Run sandboxes in OpenShell MicroVMs? macOS needs them: Docker Desktop's Linux kernel has no Landlock. (sets compute_driver = "vm" in /opt/homebrew/var/openshell/gateway.toml and restarts the gateway; OpenShell calls this driver experimental) [Y/n]
   ```

   Yes writes the driver, your uid and gid as the MicroVM sandbox user, and resources for each MicroVM (4 vCPUs, up to 4 GiB of memory and a sparse 16 GiB disk for its changes) into `gateway.toml`, with a timestamped backup, then restarts the gateway once. These settings apply to every sandbox on the gateway, including those made outside DefenseClaw.
3. Turns OpenShell's anonymous usage telemetry off, if you agree (`--upstream-telemetry` keeps it). It edits `~/.config/openshell/gateway.env`, which the Homebrew service reads, in the same change and restart.
4. Records the harnesses in `openshell.harnesses` and turns `openshell.enabled` on.
5. Builds the harness images in Docker Desktop, if you agree, and checks that each one's hooks fire and block.

It ends with:

```text
  ✓ gateway configured and restarted: it runs sandboxes in OpenShell MicroVMs
  every run works on a copy (the MicroVM driver mounts no host folders); `defenseclaw sandbox pull` brings the changes back
  the first run of each image prepares its MicroVM disk (about a minute, and about 5 GB, which OpenShell keeps)

  ✓ Done →  cd <project> && defenseclaw sandbox run claude
```

There is no mounts question on a Mac. Flags are in the [sandbox CLI reference](/docs/reference/sandbox-cli#sandbox-setup).

The **Platform** warning is expected on every Mac: it says the MicroVM driver is experimental upstream. Checks marked `-` do not apply to MicroVMs. `defenseclaw sandbox doctor --fix` applies the fixes that need only your user, after asking.

If you installed OpenShell another way and started its gateway by hand, the **Gateway service** check warns that DefenseClaw cannot restart it. Sandboxes still run on it. Setup then writes any gateway change and asks you to restart the gateway the way you started it, after you stop its sandboxes with `defenseclaw sandbox stop NAME` so their disks are saved.

## MicroVM facts

| Topic | What to know |
| --- | --- |
| Resources | Every MicroVM on the gateway gets the same vCPUs, memory and disk, set under `[openshell.drivers.vm]` in the gateway's `gateway.toml` (`/opt/homebrew/var/openshell/gateway.toml` for the Homebrew service, unless `~/.config/openshell/gateway.toml` exists). `--cpu` and `--memory` have no effect. The doctor warns when the disk for changes is under 8 GiB. |
| The sandbox user | Set for the whole gateway: every MicroVM runs as your uid and gid. |
| Disk use | About 5 GB per image the driver has started, in `~/.local/state/openshell/vm-driver`. `defenseclaw sandbox image prune` and `image rm` remove unused images and their disks. |
| Per-run settings | Claude Code and Codex settings are baked, root-owned and read-only, into a small run image for each sandbox. A run with other `--env`, credentials or model provider prepares another disk. |
| Stopping | `defenseclaw sandbox stop NAME` saves the MicroVM's disk. A gateway restart stops every MicroVM on it, so setup asks before it restarts a gateway with sandboxes running. |
| Disk full | DefenseClaw warns once when a MicroVM's overlay disk reaches 90% use. `defenseclaw sandbox status NAME` shows the warning while it runs. |

Limits on a Mac: there is no live mount and no pre-session snapshot, `sandbox undo` reverts the last `pull --apply`, `--context` is refused, the copy has no Git LFS, and OpenShell calls the driver experimental. A harness runs only after its image proves its hooks fire in a MicroVM ([which agents run](/docs/features/sandboxes#which-agents-run)).

## One OpenShell gateway per Mac

OpenShell's gateway listens on the fixed port `127.0.0.1:17670` and runs as the Homebrew service of the account that started it. A Mac runs one gateway, so only that account can run sandboxes. In a second account, `defenseclaw sandbox doctor` says that the port is held by another account's process, skips the checks that follow from it, and setup installs and starts nothing.

To hand sandboxes to another account, stop the gateway in the account that runs it, then run `defenseclaw sandbox setup` in the other one (add `--install-openshell` if OpenShell is not installed there). Several users on one machine are tracked upstream in [NVIDIA/OpenShell#4273](https://github.com/NVIDIA/OpenShell/issues/4273).

```bash
brew services stop nvidia/openshell/openshell
```

## Check it worked

`defenseclaw sandbox doctor` ends with `ready for sandboxes`, and its **Gateway compute driver** row reads `vm`.

## Undo

`defenseclaw sandbox teardown` removes this install's sandboxes, images and MicroVM disks, restores the gateway configuration from before setup (which takes the gateway off the MicroVM driver) and turns `openshell.enabled` off. OpenShell stays installed. See [`sandbox teardown`](/docs/reference/sandbox-cli#sandbox-teardown).
